# ادغام ۱۰ دسته سرویس

۴۹ پیاده‌سازی Handler و قراردادهای متناظر آن‌ها در ۱۰ سرویس تجمیع شده‌اند:
`Role`، `Faq`، `Captcha`، `AssessmentOff`، `Zarib`، `ZaribC`، `Table1`، `S`، `Nerkh` و `Abonman`.

متدهای عمومی سرویس‌ها نام مشخص دارند و overloadهای قبلی حفظ شده‌اند. مصرف‌کنندگان شامل ۱۰ کنترلر و کنترلرهای Login در API و Bridge هستند. `UpdateUsersInRoleHandler` و پردازش پس‌زمینهٔ آن مستقل باقی مانده‌اند.

## دامنهٔ تغییر

بدنهٔ محاسبات، SQL، اعتبارسنجی، پیام‌ها، لاگ و ترتیب عملیات عیناً منتقل شده‌اند. Routeها، HTTP verbها، پارامترها، مجوزها و قالب پاسخ‌های مصرف‌کنندگان حفظ شده‌اند. فایل‌های Persistence، موتور تعرفه و تولید قبض در این تغییر ویرایش نشده‌اند.

قراردادهای قدیمی فقط در پروژه‌های تست نگه داشته شده‌اند تا مقایسه با نسخهٔ قبل ممکن باشد؛ کد اجرایی پروژه از قراردادهای جدید استفاده می‌کند.

## آزمون‌های اختصاصی

- مقایسهٔ توکن‌های اجرایی ۸۰ متد سرویس با نسخهٔ ثابت قبل از ادغام؛ تنها تغییر نام‌های ثبت‌شده مجاز است. literalها، شرط‌ها، awaitها، تراکنش‌ها و متدهای کمکی نیز مقایسه می‌شوند.
- مقایسهٔ ۶۱ متد مصرف‌کننده، شامل metadata، Route، مجوز و بدنهٔ عملیات.
- مقایسهٔ رفتار ۵۲ امضای عمومی، شامل overloadها، خروجی، تغییر داده‌های حافظه، ترتیب وابستگی‌ها، اعتبارسنجی ناموفق، خطا، cancellation و تأخیر تکمیل Task.
- بررسی ثبت DI و lifetime از نوع Scoped برای هر ۱۰ سرویس.
- آزمون ۱۴ مسیر تراکنش با CommandServiceهای واقعی Dapper و اتصال ثبت‌کنندهٔ آزمایشی: متن SQL، نام و مقدار پارامترها، اشتراک تراکنش، ترتیب ثبت تغییر و لاگ، Commit، خطای اتصال/تراکنش/فرمان، تعداد رکورد منفی، لغو و Dispose.

برای تست تراکنش، نسخه‌های مخصوص تست از کد قبل و بعد استفاده می‌شوند که فقط namespace و کلاس پایهٔ اتصال آن‌ها تغییر کرده است. آزمون ساختاری یکسان بودن تمام اعضای این نسخه‌ها با منابع مربوطه را نیز کنترل می‌کند. اتصال واقعی برنامه تغییر نکرده و هیچ داده‌ای در SQL Server واقعی نوشته نمی‌شود. زمان جاری و شناسهٔ تصادفیِ ایجادشده تنها پس از کنترل معتبر بودن، برای مقایسهٔ دو اجرا نرمال می‌شوند.

## اجرای مجدد

```powershell
dotnet build Aban360.Api/Aban360.Api.csproj --no-restore -m:1
dotnet build Aban360.BrdigeApi/Aban360.BrdigeApi.csproj --no-restore -m:1
dotnet build tests/Aban360.MergedControllers.SmokeTests --no-restore -m:1 -p:BuildProjectReferences=false
dotnet run --project tests/Aban360.MergedControllers.SmokeTests --no-build --no-restore --no-launch-profile -- --critical10
dotnet run --project tests/Aban360.CriticalServiceStructure.RegressionTests
```

تحلیل ساختاری از Roslyn همراه SDK نصب‌شده استفاده می‌کند و پروژهٔ آن به SDK دات‌نت ۱۰ نیاز دارد. هدف اجرایی پروژه‌های اصلی و تست رفتاری همچنان دات‌نت ۸ است.

## نتیجهٔ اجرا

| بررسی | نتیجه |
|---|---|
| Build نهایی API و Bridge | موفق، بدون خطای کامپایل؛ هشدارهای موجود پروژه باقی هستند |
| مقایسهٔ ساختاری منابع | ۵۵۲ بررسی موفق |
| سرویس‌ها و DI | ۴۳۷ بررسی موفق؛ ۵۲ امضای متد و ۲۶۶ سناریوی قبل/بعد |
| تراکنش‌های ثبت‌شده با Dapper واقعی | ۱۵۲۶ بررسی موفق؛ ۱۴ مسیر تراکنش و ۱۷۷ سناریوی قبل/بعد |
| مجموع بررسی‌های رفتاری اختصاصی | ۱۹۶۳ بررسی موفق |
| ControllerConsolidation.SmokeTests | ۳۸۸۶ بررسی موفق |
| CriticalControllers.RegressionTests | ۱۶۳۹ بررسی موفق |
| ControllerBatch110.RegressionTests | ۲۴۲۴ بررسی موفق |
| ControllerBatch132.RegressionTests | ۱۰۷۹ بررسی موفق |
| ControllerBatch151.RegressionTests | ۵۵۲ بررسی موفق |
| اجرای عمومی MergedControllers و ControllerBatch136 | به علت ناسازگاری قدیمی CollectBills توضیح‌داده‌شده در پایین ناموفق |

در تست تراکنش `S.Create`، خواندن آخرین شناسه قبل از درج و سپس ثبت لاگ نیز با همان ترتیب و تراکنش بررسی شده است. داده‌های تولیدشده و فرمان‌های SQL در حافظه ثبت شده‌اند؛ این نتیجه جایگزین آزمون یکپارچه با SQL Server واقعی و دادهٔ نمونهٔ قبض نیست.

## محدودیت آزمون سراسری موجود

فایل انتظار `Contracts.json` هنوز مسیر `v1/collect-bills/get` را به‌صورت یک اکشن مشترک GET/POST تعریف می‌کند، در حالی که کد فعلی `CollectBillsController` از دو اکشن جداگانه با binding متفاوت استفاده می‌کند. بنابراین اجرای عمومی `MergedControllers.SmokeTests` پیش از رسیدن به تست سرویس‌ها روی همان مسیر متوقف می‌شود. مجموعهٔ `ControllerBatch136.RegressionTests` نیز این کنترلر را پوشش می‌دهد و به اختلاف تعداد اکشن‌ها می‌رسد. این کنترلر و فایل‌های انتظار آن در این ادغام تغییر نکرده‌اند.

اجرای `--critical10` تست‌های اختصاصی این مرحله را مستقل از این ناسازگاری اجرا می‌کند. تست روی SQL Server واقعی و مقایسهٔ خروجی قبض با دادهٔ واقعی در این مرحله انجام نشده است.

## نکتهٔ مستقل در SQL موجود

در `SCommandService.GetSUpdateQuery`، عبارت `ToDate=@FromDate` وجود دارد؛ در همان متد، پارامتر `toDate` نیز از ورودی تاریخ پایان ساخته می‌شود. این نکته در بررسی CommandService واقعی برای تست تراکنش مشاهده شد. این فایل در ادغام تغییر نکرده و رفتار قبلی عمداً حفظ شده است؛ اصلاح احتمالی آن نیازمند بررسی مستقل است.

## بازبینی مستقل پس از ادغام

در بازبینی مجدد، کد اجرایی تغییر نکرد. تست ساختاری برای مقایسهٔ اتصال فیلدها به پارامترهای سازندهٔ هر ۱۲ مصرف‌کننده و حفظ ترتیب مقداردهی و کنترل null تقویت شد. گزینهٔ اختیاری `--verify-head` نیز اضافه شد تا پیش از commit ادغام، بدنهٔ نسخه‌های ثابت تست مستقیماً با منابع Git HEAD مقایسه شود؛ این کنترل برای هر ۴۹ Handler و هر ۱۲ مصرف‌کننده پاس شد.

- ۶۹۸ بررسی ساختاری با مقایسهٔ مستقیم Git و کنترل سازنده‌ها موفق بود.
- ۱۹۶۳ بررسی رفتاری و تراکنش اختصاصی مجدداً موفق بود.
- پنج مجموعهٔ رگرسیون موفقِ جدول بالا مجدداً اجرا و همگی موفق شدند؛ مجموعاً ۹۵۸۰ بررسی.
- Build مجدد API و Bridge هر دو بدون خطا و هشدار موفق بودند.
- خطای جدیدی ناشی از ادغام در این بازبینی پیدا نشد. محدودیت تست واقعی SQL Server و دو ناسازگاری تست‌های قدیمی CollectBills همچنان برقرار است.
