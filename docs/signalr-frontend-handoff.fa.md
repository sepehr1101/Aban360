# راهنمای تحویل به فرانت: SignalR و کاربران آنلاین

تاریخ: ۱۵ آبان ۱۴۰۵ / 2026-11-06

## هدف و محدوده

هر کاربر می‌تواند چند اتصال هم‌زمان از تب‌ها یا دستگاه‌های مختلف داشته باشد. هدف این کار، مدیریت صحیح اتصال در هر تب، جلوگیری از اتصال و رویداد تکراری، و نمایش یک ردیف برای هر کاربر در فهرست آنلاین‌هاست.

تغییرات سمت سرور آماده شده‌اند. این سند وظایف پروژه فرانت را مشخص می‌کند؛ کد فرانت در مخزن بک‌اند موجود نیست و این موارد هنوز در فرانت پیاده‌سازی یا تأیید نشده‌اند.

## ۱. قرارداد اتصال و API

| مورد | مقدار |
| --- | --- |
| مسیر Hub | `/v1/notify-hub` |
| احراز هویت Hub | توکن دسترسی کاربر جاری |
| دریافت فهرست آنلاین‌ها | `GET /v1/online-user/get` با احراز هویت |
| بازیابی فهرست گزارش‌های کاربر جاری | `GET /v1/server-reports/by-user-id` با احراز هویت |
| محل آرایه کاربران در پاسخ | `data` |
| کلید یکتای کاربر در فهرست | `userId` |
| ثبت و حذف اتصال | خودکار در سمت سرور؛ فراخوانی دستی از فرانت لازم نیست |
| heartbeat حضور | سمت سرور؛ تایمر یا فراخوانی جدید از فرانت لازم نیست |

مسیرها نسبت به آدرس پایه API هستند. آدرس پایه را از تنظیمات محیط پروژه بگیرید.

ساختار داده هر ردیف فهرست آنلاین‌ها:

```typescript
interface OnlineUser {
  id: number;
  userId: string;
  fullName: string;
  connectDateTime: string;
  connectionId: string;
  connectionCount: number;
  connectionIds: string[];
}
```

- `connectionCount`: تعداد اتصال‌های متمایز کاربر؛ ممکن است مربوط به چند تب یا چند دستگاه باشد.
- `connectionIds`: شناسه اتصال‌های همان کاربر.
- `connectionId`، `id` و `connectDateTime`: مربوط به جدیدترین اتصال ثبت‌شده کاربر؛ این اتصال فقط نماینده است.
- `connectDateTime` زمان آخرین فعالیت یا آخرین heartbeat نیست.
- برای ثبت درخواست گزارش، شناسه اتصال **تب جاری** را از سرویس SignalR بگیرید؛ از `connectionId` موجود در جدول کاربران استفاده نکنید.

## ۲. یک سرویس اتصال مشترک در هر تب

- یک سرویس در سطح ریشه برنامه برای SignalR تعریف یا سرویس فعلی را اصلاح کنید.
- در هر تب و برای هر حساب فعال، فقط یک `HubConnection` نگه دارید.
- کامپوننت‌ها از همان سرویس استفاده کنند. ورود به صفحه، تغییر مسیر یا بازشدن مودال نباید اتصال جدید ایجاد کند.
- خروج از یک صفحه، اتصال مشترک کل برنامه را متوقف نکند؛ فقط اشتراک همان صفحه در رویدادها آزاد شود.
- اتصال مستقل در تب دیگر مجاز است. برای همه تب‌ها یک `ConnectionId` مشترک ذخیره نکنید.
- برای اشتراک اتصال بین تب‌ها، پیاده‌سازی SharedWorker یا سازوکار مشابه لازم نیست.

شروع اتصال باید در برابر فراخوانی هم‌زمان محافظت شود: اگر `start()` در حال اجراست، فراخوانی‌های بعدی همان Promise را دریافت کنند. در حالت `Connected` دوباره شروع نکنید و در حالت `Reconnecting`، مسیر موازی `start()` نسازید.

## ۳. اتصال مجدد و توکن

پیکربندی پایه پیشنهادی با بسته `@microsoft/signalr`:

```typescript
import { HubConnectionBuilder } from "@microsoft/signalr";

function createNotifyConnection(
  apiBaseUrl: string,
  getCurrentAccessToken: () => string | Promise<string>
) {
  return new HubConnectionBuilder()
    .withUrl(`${apiBaseUrl.replace(/\/$/, "")}/v1/notify-hub`, {
      accessTokenFactory: getCurrentAccessToken
    })
    .withAutomaticReconnect([0, 2000, 10000, 30000])
    .build();
}
```

این نمونه فقط سازنده اتصال است؛ کنترل شروع، پایان، تلاش مجدد و رویدادها باید در سرویس مشترک انجام شود.

الزامات:

1. `accessTokenFactory` در هر فراخوانی، توکن جاری را از سرویس احراز هویت بگیرد؛ توکن زمان ساخت اتصال را در closure ثابت نکنید.
2. خطای اولین `start()` جداگانه مدیریت شود. `withAutomaticReconnect` فقط قطع اتصالِ برقرارشده را پوشش می‌دهد.
3. برای شروع ناموفق و پایان تلاش‌های خودکار، سیاست تلاش مجدد محدود با فاصله افزایشی و امکان تلاش دستی داشته باشید؛ حلقه بی‌وقفه ایجاد نکنید.
4. در خطای احراز هویت، از سازوکار موجود نوسازی توکن یا ورود مجدد استفاده کنید؛ با توکن منقضی تلاش بی‌پایان نکنید.
5. در `onreconnecting` شناسه اتصال قابل استفاده برای درخواست جدید را نامعتبر کنید و وضعیت «در حال اتصال مجدد» نمایش دهید.
6. پس از شروع موفق و در `onreconnected`، شناسه اتصال جاری را از `connection.connectionId` تازه کنید. در نبود شناسه، عملیات نیازمند آن را متوقف نگه دارید.
7. بعد از `onreconnected`، اتصال را دستی در دیتابیس ثبت نکنید و handlerهای پیام را دوباره ثبت نکنید.
8. در `onclose` وضعیت قطع اتصال را نمایش دهید. تلاش مجدد فقط زمانی مجاز است که کاربر هنوز وارد حساب است و توقف عمدی نبوده است.
9. تایمرهای retry مربوط به نشست قبلی، بعد از خروج یا تغییر حساب لغو شوند. تکمیل دیرهنگام یک Promise قدیمی نباید اتصال حساب قبلی را دوباره فعال کند.
10. اگر بک‌اند گزینه `SignalR:CloseOnAuthenticationExpiration` را فعال کند، با انقضای JWT اتصال Hub بسته می‌شود؛ مسیر reconnect باید از `accessTokenFactory` توکن تازه دریافت کند. برای سازگاری با کلاینت فعلی، این گزینه در نبود تنظیم صریح غیرفعال است. پس از تأیید آزمون نوسازی توکن و reconnect در فرانت، تیم بک‌اند می‌تواند آن را فعال کند. در .NET 8، تمدید توکن در فرانت، به‌تنهایی هویت اتصال WebSocket موجود را تازه نمی‌کند.

پشتیبانی قبلی از توکن query در مسیرهای REST و لینک‌های دانلود حفظ شده است. اگر دانلود با لینک حاوی `access_token` انجام می‌شود، برای سازگاری با این نسخه نیاز به تغییر اجباری ندارد. هدر `Authorization: Bearer ...` نیز قابل استفاده است و نسبت به query اولویت دارد. تنظیمات CORS موجود در این بازبینی تغییر نکرده‌اند.

برای درخواست جدیدِ نیازمند `connectionId`، از مقدار جاری سرویس استفاده کنید. مقدار را یک‌بار در ابتدای عمر صفحه ذخیره نکنید.

## ۴. مدیریت رویدادها بدون اجرای تکراری

رویدادهای فعلی سرور:

| رویداد | داده دریافتی |
| --- | --- |
| `BroadcastMessage` | `title`, `message`, `color`, `seconds` |
| `InformReportCompletion` | `reportId`, `reportTitle`, `message` |

- handlerهای SignalR یک‌بار برای همان نمونه اتصال، پیش از شروع آن ثبت شوند.
- بعد از reconnect همان نمونه، ثبت مجدد `.on(...)` لازم نیست.
- اگر لازم است handler حذف شود، مرجع همان تابع را به `.off(eventName, handler)` بدهید.
- کامپوننت‌ها از خروجی سرویس مشترک subscribe کنند و هنگام نابودی، فقط subscription خود را آزاد کنند.
- پاک‌کردن تمام handlerهای یک رویداد توسط یک کامپوننت، نباید دریافت پیام سایر بخش‌ها را مختل کند.
- دریافت Broadcast در هر تب باز، طبیعی است. معیار رفع تکرار این است که در **هر تب**، هر دریافت پیام فقط یک‌بار پردازش شود.

## ۵. خروج از حساب و تغییر حساب

ترتیب خروج یا تغییر کاربر:

1. توقف عمدی را در سرویس مشخص کنید تا callbackهای اتصال، retry جدید ایجاد نکنند.
2. تایمرهای retry و تلاش‌های برنامه‌ریزی‌شده نشست قبلی را لغو کنید.
3. `await connection.stop()` را اجرا کنید.
4. شناسه اتصال، وضعیت اتصال و داده‌های مخصوص حساب قبلی را پاک کنید.
5. برای حساب جدید، اتصال را با توکن همان حساب برقرار کنید.

بستن یک تب نباید باعث بستن تمام اتصال‌های کاربر شود. برای قطع اتصال همه تب‌ها، درخواست جدید به بک‌اند اضافه نکنید. به اجرای حتمی `beforeunload` نیز متکی نباشید؛ تشخیص قطع و انقضا سمت سرور انجام می‌شود.

اگر خروج از حساب در محصول باید در تمام تب‌ها اعمال شود، از سازوکار هماهنگی احراز هویت موجود پروژه استفاده کنید تا هر تب اتصال خودش را متوقف کند.

## ۶. اصلاح صفحه کاربران آنلاین

- داده‌ها از `GET /v1/online-user/get` و آرایه `data` خوانده شوند.
- پاسخ موفق جدید جایگزین snapshot قبلی شود؛ آن را به آرایه قبلی append نکنید.
- کلید ردیف یا `trackBy` برابر `userId` باشد، نه نام کاربر، شماره ردیف یا `connectionId`.
- افراد هم‌نام با `userId` متفاوت، دو کاربر مستقل هستند؛ با `fullName` تجمیع نکنید.
- تعداد کاربران آنلاین برابر تعداد ردیف‌های پاسخ است. مجموع `connectionCount` تعداد اتصال‌هاست، نه تعداد کاربران.
- در صورت نمایش تعداد اتصال‌ها، عنوان ستون «تعداد اتصال» باشد، نه «تعداد تب».
- وضعیت بارگذاری، خطای دریافت و فهرست خالی جدا نمایش داده شوند. شکست API به معنی صفر کاربر آنلاین نیست.
- اگر polling وجود دارد، هم‌زمان فقط یک دریافت انجام شود. پاسخ قدیمی‌تر نباید snapshot جدیدتر را بازنویسی کند.
- polling در زمان فعال‌بودن صفحه اجرا و با خروج از صفحه متوقف شود. فاصله ۱۰ تا ۱۵ ثانیه پیشنهاد اولیه است و با الگوی فعلی پروژه قابل تنظیم است.
- در صورت بازگشت به صفحه یا بازیابی اتصال، فهرست را دوباره دریافت کنید.

فهرست آنلاین‌ها یک snapshot سرور است. هنگام reconnect ممکن است اتصال قبلی برای مدت کوتاهی کنار اتصال جدید باقی بماند؛ این وضعیت به معنی دو کاربر نیست.

## ۷. گزارش‌های پس‌زمینه و بازیابی اعلان

در بک‌اند بازبینی‌شده، پس از ثبت موفق تکمیل گزارش در دیتابیس، رویداد `InformReportCompletion` به شناسه مالک گزارش و تمام اتصال‌های جاری او ارسال می‌شود. مقصد اعلان دیگر به `ConnectionId` قدیمیِ زمان درخواست محدود نیست.

- دریافت اعلان در چند تب همان کاربر طبیعی است؛ پردازش و نمایش در هر تب یک‌بار انجام شود.
- `reportId` را کلید به‌روزرسانی گزارش و کنترل اعلان تکراری در همان تب قرار دهید.
- تغییر مسیر اعلان به همه تب‌ها نباید باعث دانلود خودکار چندباره یا بازکردن خودکار فایل در تمام تب‌ها شود؛ فهرست و وضعیت گزارش را تازه کنید و دانلود را به اقدام کاربر وابسته نگه دارید.
- اگر کاربر هنگام ارسال اعلان هیچ اتصال فعالی نداشته باشد، اعلان ذخیره و پس از reconnect بازپخش نمی‌شود.
- خطای ارسال اعلان باعث تولید دوباره فایل گزارش نمی‌شود؛ فایل تکمیل‌شده از API گزارش‌ها قابل بازیابی است.

فرانت نباید تکمیل گزارش را صرفاً از دریافت رویداد نتیجه بگیرد. پس از اتصال مجدد یا بازگشت به صفحه گزارش‌ها، وضعیت گزارش‌های کاربر را از API موجود گزارش‌ها بازیابی کند. اعلان، محرک تازه‌کردن وضعیت باشد؛ منبع نهایی، وضعیت گزارش در API است.

دریافت همه تب‌ها در چند پردازش مستقل، به تنظیم backplane سمت زیرساخت وابسته است. برای یک پردازش API، ارسال کاربرمحور تمام اتصال‌های همان پردازش را پوشش می‌دهد.

## ۸. پیش‌نیاز هماهنگی انتشار با بک‌اند

تیم بک‌اند یا مسئول استقرار باید **پیش از انتشار نسخه جدید API** اسکریپت زیر را در دیتابیس **Aban360** اجرا کند:

`Aban360.CommunicationPool.Persistence/Migrations/Manual/001_HubEventPresence_Aban360.sql`

این اسکریپت مربوط به Atlas نیست و وظیفه اجرای آن با فرانت نیست. اجرای خودکار migration در startup فعلی غیرفعال است. بعد از انتشار، مرورگر باید به نسخه جدید متصل شود؛ برای تست انتشار می‌توان صفحه را reload کرد.

سرور هر ۳۰ ثانیه اتصال‌های باز را تأیید می‌کند. اتصال بدون تأیید، پس از دو دقیقه از آخرین تأیید از فهرست آنلاین‌ها کنار می‌رود. فرانت برای این کار متد `Ping` یا `Heartbeat` جدیدی صدا نزند؛ چنین متدی در قرارداد فعلی Hub وجود ندارد.

در اجرای مستقیم روی یک سرور و یک پردازش، تنظیم Redis یا Load Balancer جزو وظایف این تغییر نیست. اگر محیط واقعاً چند پردازش مستقل API دارد، تیم بک‌اند/زیرساخت باید اشتراک پیام‌های SignalR بین پردازش‌ها را جداگانه بررسی کند.

## ۹. معیار پذیرش و سناریوهای تست

تست‌ها پس از انتشار بک‌اند جدید و اجرای اسکریپت انجام شوند. نتایج مربوط به تعداد اتصال‌ها بعد از پایدارشدن اتصال و دریافت snapshot تازه بررسی شوند.

| سناریو | نتیجه مورد انتظار |
| --- | --- |
| چند کامپوننت هم‌زمان به سرویس اتصال نیاز دارند | در همان تب فقط یک اتصال و یک عملیات شروع ایجاد شود. |
| جابه‌جایی مکرر بین صفحات | اتصال اضافی ساخته نشود و handlerها زیاد نشوند. |
| یک حساب در دو تب | یک ردیف کاربر با دو اتصال نمایش داده شود. |
| بستن یکی از دو تب | تب دیگر متصل بماند و کاربر از فهرست حذف نشود؛ تعداد اتصال‌ها پس از تشخیص قطع و دریافت فهرست تازه کاهش یابد. |
| دو کاربر با نام یکسان | دو ردیف مستقل بر اساس `userId` نمایش داده شود. |
| قطع و وصل شبکه | وضعیت reconnect دیده شود؛ بعد از اتصال موفق، درخواست جدید از شناسه جاری استفاده کند. |
| قطع شبکه هنگام شروع اولیه | تلاش مجددِ محدود بدون ساخت اتصال موازی انجام شود. |
| دریافت یک Broadcast پس از چند reconnect و تغییر صفحه | در هر تب فقط یک‌بار پردازش و نمایش داده شود. |
| خروج در زمان reconnect یا retry | اتصال بعد از خروج خودکار دوباره برقرار نشود. |
| انقضای JWT با فعال‌بودن گزینه بستن اتصال | سرور اتصال را ببندد و کلاینت با توکن تازه و بدون ساخت اتصال موازی برگردد؛ پیش از فعال‌سازی این گزینه تأیید شود. |
| تغییر حساب در همان تب | اتصال و داده حساب قبلی پاک شود و اتصال جدید متعلق به حساب جدید باشد. |
| چند بار تازه‌کردن کاربران آنلاین | ردیف‌ها append نشوند و تعداد کاربران رشد کاذب نکند. |
| خطای API کاربران آنلاین | خطا نمایش داده شود؛ وضعیت به‌اشتباه «هیچ کاربری آنلاین نیست» نشود. |
| reconnect هنگام تهیه گزارش | وضعیت گزارش از API بازیابی شود، حتی اگر اعلان تکمیل دریافت نشود. |
| تکمیل یک گزارش با دو تب متصل | هر تب همان کاربر اعلان را یک‌بار پردازش کند؛ کاربر دیگر مخاطب اعلان نباشد. |
| توقف ناگهانی سرور بدون reconnect | رکوردهای قبلی پس از پایان مهلت حضور و دریافت موفق فهرست تازه، آنلاین نمایش داده نشوند. |
| اتصال سالم بیش از ۲۴ ساعت | کاربر همچنان آنلاین باقی بماند. |

تحویل فرانت شامل تغییر سرویس مشترک اتصال، تغییر صفحه کاربران آنلاین و نتیجه تست سناریوهای مرتبط باشد. کد کلاینت در این مخزن بررسی نشده است؛ اگر یکی از رفتارهای بالا از قبل درست پیاده شده، حفظ آن و ثبت نتیجه تست کافی است.
