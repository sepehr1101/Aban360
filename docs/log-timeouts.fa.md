# پیگیری timeout گزارش‌های لاگ

## تغییرات کد

- در گزارش HTTP، فیلدهای XML برحسب نوع گزارش و فیلترهای ارسالی انتخاب می‌شوند. برای مثال گزارش کاربران بدون فیلتر مسیر، TraceId و مشخصات مسیر را استخراج نمی‌کند.
- فیلترهای اختیاری فقط هنگام ارسال در کوئری قرار می‌گیرند و مقدار آن‌ها همچنان پارامتری است.
- `OPTION (RECOMPILE)` برای گزارش HTTP اضافه شد تا بهینه‌ساز برای بازه و فیلترهای همان درخواست پلن تولید کند. این کار هزینهٔ کامپایل در هر درخواست دارد؛ اثر نهایی باید با دادهٔ واقعی سنجیده شود.
- در گزارش عملیات، تابع تاریخ از روی ستون `RegisterDateTime` حذف شد؛ جست‌وجو اکنون با شروع روز اول و پایانِ غیرشامل روز بعد از تاریخ پایان انجام می‌شود. بنابراین پوشش کامل روز پایان حفظ می‌شود و شرط زمانی امکان استفاده از ایندکس را دارد. خروجی از جدیدترین رکورد مرتب می‌شود.
- timeout صرفاً افزایش داده نشده و سقف شمارش گزارش‌ها کاهش نیافته است.

## اقدامات دیتابیس

اسکریپت‌های آماده‌شده و کاربرد آن‌ها:

1. `Aban360.SystemPool.Persistence/Scripts/LoggingReadDiagnostics.sql`: بررسی فقط‌خواندنی نوع ستون‌ها، ایندکس‌های موجود، تعداد تقریبی لاگ و در صورت داشتن مجوز، درخواست‌های در حال اجرا و انتظار/مسدودشدگی آن‌ها. روی سرور API اجرا شود؛ اگر دیتابیس گزارش روی سرور دیگری است، بخش مربوط به `CustomerWarehouse` باید آنجا اجرا شود.
2. `Aban360.SystemPool.Persistence/Scripts/LoggingReadIndexes.sql`: ایندکس زمانی لاگ سیستم و ایندکس سطح/زمان. بررسی کلید اول ایندکس موجود برای زمان اضافه شده تا ایندکس مناسب با نام متفاوت دوباره ساخته نشود.
3. `Aban360.SystemPool.Persistence/Scripts/OperationLogReadIndex.sql`: ایندکس زمانی لاگ عملیات، با بررسی وجود ایندکس مناسب قبلی.

ایندکس‌ها در پنجرهٔ نگهداری و پس از بررسی خروجی تشخیص اجرا شوند؛ ساخت ایندکس روی جدول بزرگ هزینهٔ دیسک و قفل دارد. اسکریپت‌ها منتظر ماندن برای قفل را به ۵ ثانیه محدود می‌کنند و ممکن است در زمان شلوغی نیاز به اجرای مجدد داشته باشند.

پس از استقرار کد، همان درخواست مشکل‌دار با همان فیلترها دوباره بررسی و پلن اجرای واقعی و `STATISTICS IO, TIME` ثبت شود. بازهٔ کوتاه‌تر می‌تواند برای مقایسه کمک کند؛ `PageSize` کوچک‌تر به‌تنهایی هزینهٔ محاسبهٔ آمار کل بازه را حذف نمی‌کند.

## نتیجهٔ بررسی

۱۲۲ بررسی مشاهدهٔ لاگ و ساخت کوئری‌های ۴ نوع گزارش با تمام ترکیب‌های حضور/عدم حضور دو فیلتر موفق بودند. تست‌های قبلی هندلر گزارش HTTP نیز موفق بودند. بررسی ساخت کوئری، اجرای SQL و سنجش کارایی روی SQL Server نیست.

پلن اجرا و رفع timeout در سرور واقعی هنوز تأیید نشده‌اند. اگر هزینهٔ اصلی همچنان XML باشد، گام بعدی بررسی ذخیرهٔ فیلدهای گزارش در ستون‌های مستقل یا تجمیع از پیش محاسبه‌شده است؛ این تغییرات در این مرحله اعمال نشده‌اند.

## اجرای ایندکس‌ها در ۲۰۲۶/۱۱/۰۲

طبق درخواست اجرای ایندکس‌ها، اتصال به دیتابیس `Aban360` تنظیم‌شده در پروژه برقرار شد. ایندکس زمانی وجود نداشت و ساخته شد. بررسی ساختار واقعی نشان داد ستون `Level` از نوع `nvarchar(max)` است؛ ساخت `(Level, TimeStamp)` با خطای SQL شمارهٔ ۱۹۱۹ رد شد. به‌جای آن، همان ایندکس زمانی به شکل زیر تکمیل شد:

```sql
IX_Logs_TimeStamp ON dbo.Logs (TimeStamp DESC) INCLUDE (Level)
```

فعال بودن ایندکس و وجود `Level` به‌عنوان ستون INCLUDE از متادیتای SQL Server تأیید شد. اسکریپت `LoggingReadIndexes.sql` با این ساختار سازگار شد و اجرای مجدد آن نیز بدون ساخت ایندکس تکراری موفق بود. این ایندکس برای محدود کردن بازهٔ زمانی و بررسی سطح از روی ایندکس مفید است؛ معادل جست‌وجوی مستقیم با کلید `(Level, TimeStamp)` نیست و هزینهٔ XML گزارش‌های HTTP را حذف نمی‌کند.

اتصال به `CustomerWarehouse` روی سرور تنظیم‌شدهٔ گزارش، با SqlClient و sqlcmd در مرحلهٔ prelogin قطع شد. بنابراین ایندکس `IX_OpLog_RegisterDateTime` در این اجرا ساخته یا تأیید نشد. برای تکمیل آن، دسترسی اتصال به سرور گزارش باید برقرار شود؛ خطای مشاهده‌شده، قطع ارتباط هنگام handshake با کد 10054 بود و علت دقیق سمت سرور تأیید نشده است.
