# بازبینی SignalR

تاریخ: 2026-11-06

## دامنه بررسی

چرخه اتصال و قطع `NotifyHub`، ثبت اتصال‌های چند تب، heartbeat و انقضای حضور، فهرست کاربران آنلاین، احراز هویت Hub، ارسال اعلان تکمیل گزارش، ثبت نتیجه گزارش و ثبت سرویس‌ها بررسی شد. تنظیمات CORS موجود بنا به درخواست کاربر تغییر نکرده است.

## نقص‌های تأییدشده و اصلاح‌شده

| اولویت | نقص قبلی | اثر | اصلاح |
| --- | --- | --- | --- |
| P1 | اعلان گزارش به `ConnectionId` زمان درخواست وابسته بود. | پس از reconnect مقصد قدیمی می‌شد؛ سایر تب‌های کاربر اعلان نمی‌گرفتند. | `ReportCompletionNotifier` اعلان را به `UserId` مالک گزارش و اتصال‌های جاری او ارسال می‌کند. شناسه اتصال ارسالی کلاینت در تعیین مخاطب اعلان استفاده نمی‌شود. |
| P1 | handler و سرویس ثبت تکمیل گزارش `async void` بودند. | اعلان می‌توانست قبل از ثبت تکمیل در دیتابیس ارسال شود؛ خطای ذخیره‌سازی قابل انتظار و مدیریت توسط caller نبود. | هر دو لایه `Task` برمی‌گردانند و فراخوانی‌های تولید گزارش پیش از ادامه آنها را `await` می‌کنند. |
| P1 | ارسال اعلان `await` نمی‌شد. | پایان ارسال و خطای آن تحت کنترل نبود. | ارسال قابل انتظار است؛ خطای انتقال ثبت می‌شود و باعث تولید مجدد گزارش تکمیل‌شده نمی‌شود. |
| P2 | بستن اتصال با انقضای JWT قابل تنظیم نبود. | فعال‌سازی اجباری این رفتار می‌توانست کلاینت فاقد reconnect با توکن تازه را قطع کند. | گزینه `SignalR:CloseOnAuthenticationExpiration` اضافه شد؛ پیش‌فرض همان رفتار قبلی است و پس از تأیید فرانت قابل فعال‌سازی است. |
| P2 | خواندن `access_token` از query هدر درخواست را تغییر می‌داد. | هدر به‌طور غیرضروری بازنویسی می‌شد. | فقط یک مقدار پذیرفته می‌شود، هدر موجود اولویت دارد و هدر بازنویسی نمی‌شود. پذیرش query token در مسیرهای قبلی برای سازگاری با لینک‌های دانلود و کلاینت‌های موجود حفظ شده است. |
| P2 | هر دور heartbeat مهلت کلی مشخصی نداشت. | عملیات کند دیتابیس می‌توانست دورهای بعدی تمدید را عقب بیندازد. | توکن لغو با مهلت ۲۰ ثانیه برای هر دور اضافه شد؛ خطا ثبت می‌شود و حلقه دوره‌ای ادامه پیدا می‌کند. |
| P2 | اتصال‌های دیتابیس متدهای ثبت قطع اتصال آزاد نمی‌شدند. | خطر مصرف تدریجی connection pool وجود داشت. | اتصال‌ها با `await using` آزاد می‌شوند. |
| P2 | جست‌وجوی `ConnectionId` ایندکس اختصاصی نداشت. | با رشد تاریخچه، تمدید حضور و ثبت قطع می‌توانست نیازمند پیمایش بیشتر شود. | ایندکس `IX_HubEvent_ConnectionId` به اسکریپت دستی اضافه شد. |

وابستگی استفاده‌نشده و کد کامنت‌شده بستن تمام اتصال‌ها در handler اتصال جدید نیز حذف شد؛ اتصال یک تب نباید اتصال سایر تب‌های کاربر را ببندد.

## رفتارهایی که دوباره بررسی شدند

- یک ردیف خروجی برای هر `UserId`، نه برای هر نام یا اتصال.
- شمارش شناسه اتصال‌های متمایز و حفظ کاربران هم‌نام با شناسه متفاوت.
- حفظ اتصال سایر تب‌ها هنگام قطع یک تب.
- ثبت شناسه جدید هنگام reconnect.
- توقف تمدید یک اتصال بسته‌شده حتی هنگام خطای ثبت قطع در دیتابیس.
- حل سرویس‌های heartbeat و اعلان از مسیر ثبت واقعی برنامه.
- انتقال توکن لغو به ذخیره‌سازی نتیجه گزارش.

## هماهنگی لازم با فرانت

نسخه به‌روز `docs/signalr-frontend-handoff.fa.md` مبنای تحویل باشد:

1. توکن تازه در `accessTokenFactory` و تأیید reconnect پیش از فعال‌سازی بستن اتصال هنگام انقضای JWT.
2. دریافت اعلان گزارش در هر تب کاربر و کنترل پردازش تکراری با `reportId`؛ از دانلود خودکار در تمام تب‌ها اجتناب شود.
3. هدر `Authorization: Bearer ...` برای REST قابل استفاده است؛ لینک‌های دانلود موجود دارای `access_token` نیز مانند قبل پشتیبانی می‌شوند. تغییر فرانت برای مهاجرت اجباری این لینک‌ها لازم نیست.
4. دریافت مجدد وضعیت گزارش از API بعد از reconnect؛ اعلان، پیام ماندگار یا رسید دریافت کلاینت نیست.

## استقرار و محدوده اعتبار بررسی

- اسکریپت `Aban360.CommunicationPool.Persistence/Migrations/Manual/001_HubEventPresence_Aban360.sql` باید در دیتابیس **Aban360** اجرا شود. این فایل روی دیتابیس در این بررسی اجرا نشده است.
- اگر نسخه قبلی اسکریپت اجرا شده، اجرای دوباره نسخه فعلی ایندکس تازه را اضافه می‌کند و اطلاعات موجود را حذف نمی‌کند.
- heartbeat، در دسترس‌بودن اتصال Hub را نشان می‌دهد؛ به معنی فعالیت اخیر ماوس یا صفحه فعال کاربر نیست.
- `await` ارسال به معنی رسید تحویل کلاینت نیست. هنگام قطع شبکه، اعلان ممکن است از دست برود و API گزارش‌ها مسیر بازیابی است.
- تغییر نقش یا لغو حساب، هویت اتصال موجود را فوراً بازخوانی نمی‌کند؛ اتصال مجدد باعث احراز هویت دوباره می‌شود. اگر گزینه بستن اتصال هنگام انقضا فعال نباشد، انقضای JWT به‌تنهایی WebSocket موجود را نمی‌بندد. قطع فوری همه نشست‌ها در واکنش به تغییر نقش، قابلیت جداگانه‌ای است.
- حضور چند پردازش از دیتابیس مشترک خوانده می‌شود؛ پیام‌رسانی بین چند پردازش مستقل همچنان به backplane نیاز دارد. در این بررسی Redis یا تنظیمات سرور اصلی تغییر نکرده است.
- آزمون‌ها با سرویس‌های شبیه‌سازی‌شده اجرا می‌شوند؛ اتصال به SQL Server اصلی، اتصال مرورگر واقعی، انقضای JWT روی WebSocket واقعی و تنظیمات IIS در این بررسی یکپارچه اجرا نشده‌اند. برای انتشار، سناریوهای سند فرانت روی محیط آزمایشی بررسی شوند.
