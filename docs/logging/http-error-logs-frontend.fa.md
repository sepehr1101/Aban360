# راهنمای فرانت: مشاهده خطاهای HTTP

این سند قرارداد API و رفتار مورد انتظار صفحه «خطاهای HTTP» در بخش Logging است. از کلاینت HTTP، احراز هویت، انتخابگر تاریخ شمسی و جدول موجود پروژه فرانت استفاده کنید.

## ۱. مسیر و دسترسی

| مورد | مقدار |
| --- | --- |
| متد | `GET` |
| مسیر نسبت به Base URL فعلی برنامه | `/v1/logging/errors` |
| ورودی | Query string؛ بدون body |
| احراز هویت | توکن معتبر با هدر `Authorization: Bearer <access_token>` |
| مجوز | نقش ادمین تنظیم‌شده در `ApiSettings:AdminRoleName` |
| پاسخ موفق | HTTP 200؛ آرایه خطاها در `data` |

صفحه برای کاربر مجاز نمایش داده شود. کنترل نهایی دسترسی در سرور انجام می‌شود. مقدار نام نقش را از الگوی دسترسی فعلی فرانت بگیرید.

## ۲. فیلترها و پارامترها

| پارامتر | نوع | الزامی | پیش‌فرض سرور | قاعده |
| --- | --- | --- | --- | --- |
| `statusCodeClass` | string | بله | ندارد | فقط `4XX` یا `5XX`؛ حروف کوچک و فاصله ابتدا و انتها پذیرفته می‌شود |
| `fromDate` | string | بله | ندارد | تاریخ شمسی معتبر با قالب `yyyy/MM/dd` |
| `toDate` | string | بله | ندارد | تاریخ شمسی معتبر با قالب `yyyy/MM/dd` |
| `fromTime` | string | بله | ندارد | ساعت ۲۴ ساعته با قالب `HH:mm` |
| `toTime` | string | بله | ندارد | ساعت ۲۴ ساعته با قالب `HH:mm` |
| `page` | integer | خیر | `1` | از ۱ تا `2147483647` |
| `pageSize` | integer | خیر | `50` | از ۱ تا ۲۰۰ |

گزینه‌های انتخاب گروه:

- «خطاهای 4XX»: کدهای ۴۰۰ تا ۴۹۹، شامل 400، 401، 403، 404 و غیره.
- «خطاهای 5XX»: کدهای ۵۰۰ تا ۵۹۹، شامل 500، 502، 503 و غیره.

مقدار ارسالی رشته `4XX` یا `5XX` است؛ عدد `400`، مقدار `4` و گزینه «همه» پشتیبانی نمی‌شوند. فیلتر کد تکی مثل 401، متد، کاربر، مسیر، متن پیام و مرتب‌سازی دلخواه در این endpoint وجود ندارد.

## ۳. معنای بازه تاریخ و ساعت

شروع و پایان، هرکدام یک تاریخ و ساعت کامل هستند. بازه **پیوسته** است و تمام دقیقه پایان را شامل می‌شود.

| انتخاب کاربر | محدوده جست‌وجو |
| --- | --- |
| `1405/08/01 08:00` تا `1405/08/01 18:30` | از ۰۸:۰۰:۰۰ تا قبل از ۱۸:۳۱:۰۰ همان روز |
| `1405/08/01 08:00` تا `1405/08/02 18:30` | شامل ساعات شب بین دو روز نیز می‌شود |
| `1405/08/01 00:00` تا `1405/08/01 23:59` | کل روز اول آبان |
| تاریخ یکسان و ساعت `10:20` در هر دو سمت | تمام دقیقه ۱۰:۲۰ همان روز |

قواعد ارسال:

- زمان شروع نباید بعد از پایان باشد؛ برابر بودن مجاز است.
- فاصله دو مقدار واردشده حداکثر ۳۱ روز است.
- تاریخ را با کتابخانه تقویم شمسی موجود اعتبارسنجی کنید؛ طول همه ماه‌ها یکسان نیست.
- ارقام لاتین، فارسی و عربی پذیرفته می‌شوند؛ برای یکدستی، ارسال ارقام لاتین مناسب است.
- ثانیه، ISO date و مقدار دارای منطقه زمانی ارسال نکنید.
- تاریخ و ساعت را به UTC یا با `toISOString()` تبدیل نکنید؛ رشته انتخاب‌شده شمسی و ساعت را مستقیماً ارسال کنید.
- یک دقیقه به پایان اضافه نکنید؛ سرور این تبدیل را انجام می‌دهد.

مبنای زمانی با لاگ ذخیره‌شده و گزارش‌های فعلی سرور یکسان است. این API منطقه زمانی مستقلی در ورودی یا خروجی ندارد.

## ۴. نمونه درخواست

```http
GET /v1/logging/errors?statusCodeClass=4XX&fromDate=1405%2F08%2F01&toDate=1405%2F08%2F12&fromTime=08%3A00&toTime=18%3A30&page=1&pageSize=50
Authorization: Bearer <access_token>
Accept: application/json
```

برای دریافت خطاهای سرور، همین درخواست را با `statusCodeClass=5XX` ارسال کنید. برای ساخت URL از `URLSearchParams` یا امکانات کلاینت فعلی استفاده کنید.

## ۵. پاسخ موفق

نمونه زیر صرفاً شکل پاسخ را نشان می‌دهد:

```json
{
  "success": true,
  "httpStatusCode": 200,
  "successMessage": "درخواست با موفقیت پردازش شد",
  "data": [
    {
      "id": 12345,
      "dateJalali": "1405/08/12",
      "time": "10:24:35",
      "statusCode": 401,
      "requestMethod": "GET",
      "routeTemplate": "v1/example/{id}",
      "traceId": "example-trace-id",
      "userId": null,
      "message": "HTTP GET v1/example/{id} completed 401 in 2 ms; TraceId example-trace-id; UserId null"
    }
  ],
  "errors": null,
  "warnings": null,
  "meta": {
    "nextAction": "",
    "serverDateTime": "2026-11-03T10:25:00"
  }
}
```

| فیلد ردیف | نوع JSON | کاربرد |
| --- | --- | --- |
| `id` | number، عدد صحیح ۶۴ بیتی در سرور | شناسه لاگ؛ برای کلید ردیف استفاده شود، روی آن محاسبه انجام ندهید |
| `dateJalali` | string | تاریخ شمسی با قالب `yyyy/MM/dd` |
| `time` | string | ساعت رخداد با قالب `HH:mm:ss` |
| `statusCode` | number | کد واقعی پاسخ درخواست ثبت‌شده، مانند 400 یا 401 |
| `requestMethod` | string یا null | متد درخواست |
| `routeTemplate` | string یا null | قالب مسیر، نه URL واقعی؛ ممکن است `<unmatched>` باشد |
| `traceId` | string یا null | شناسه پیگیری برای ارجاع به پشتیبانی؛ قابل کپی |
| `userId` | string یا null | شناسه کاربر؛ برای درخواست بدون احراز هویت ممکن است null باشد |
| `message` | string یا null | پیام ثبت پایان درخواست؛ متن بدنه پاسخ خطا یا stack trace نیست |

هر ردیف یک درخواست است؛ تعداد رخدادها به تفکیک کد، در این API تجمیع نمی‌شود. ترتیب پاسخ ثابت است: تاریخ و ساعت نزولی، سپس شناسه نزولی. مقادیر null را با «—» نمایش دهید. پیام و مسیر را به‌صورت متن معمولی رندر کنید و برای متن طولانی امکان مشاهده کامل در جزئیات ردیف قرار دهید.

`statusCode: 401` داخل یک ردیف به معنی انقضای نشست فعلی کاربر نیست؛ آن را از HTTP 401 پاسخ فراخوانی API جدا در نظر بگیرید.

شناسه `id` در JSON عدد است؛ اگر از محدوده صحیح امن JavaScript بزرگ‌تر باشد، پارسر معمولی دقت آن را از دست می‌دهد. برای نیاز به حفظ دقیق چنین شناسه‌هایی باید قرارداد خروجی یا روش parsing با بک‌اند هماهنگ شود؛ تبدیل عدد به رشته بعد از `JSON.parse` دقت ازدست‌رفته را بازیابی نمی‌کند.

## ۶. صفحه‌بندی و نتیجه خالی

`data` همیشه در پاسخ موفق آرایه است. نتیجه خالی با HTTP 200 و `data: []` برمی‌گردد.

- API فیلد `totalCount`، `totalPages` یا `hasMore` ندارد؛ تعداد کل نتیجه را از طول یک صفحه محاسبه نکنید.
- از دکمه‌های «قبلی» و «بعدی» استفاده کنید؛ قبلی در صفحه اول غیرفعال باشد.
- اگر تعداد ردیف‌ها کمتر از `pageSize` بود، صفحه بعد وجود ندارد.
- اگر تعداد ردیف‌ها برابر `pageSize` بود، صفحه بعد ممکن است خالی باشد. در این حالت پیام «نتیجه دیگری وجود ندارد» و امکان برگشت به صفحه قبل را نشان دهید.
- با تغییر فیلترهای اعمال‌شده یا اندازه صفحه، `page` را به ۱ بازگردانید.
- صفحه‌بندی مبتنی بر offset است؛ ورود لاگ جدید هنگام مرور می‌تواند ردیف‌های صفحات را جابه‌جا کند. API snapshot ثابت ارائه نمی‌دهد.

## ۷. مدیریت خطا

| HTTP status فراخوانی API | رفتار فرانت |
| --- | --- |
| `400` | پیام اعتبارسنجی را نمایش دهید؛ ورودی‌ها حفظ شوند |
| `401` | از جریان احراز هویت و تمدید توکن فعلی پروژه استفاده کنید |
| `403` | پیام «دسترسی به مشاهده خطاها ندارید» نمایش دهید |
| `500` | پیام خطای دریافت اطلاعات و امکان تلاش مجدد نمایش دهید |
| قطع شبکه | پیام عدم ارتباط و تلاش مجدد؛ نتیجه را خالی موفق معرفی نکنید |

خطای کسب‌وکار مانند بازه معکوس از envelope استاندارد برمی‌گردد؛ متن نمونه:

```json
{
  "success": false,
  "httpStatusCode": 400,
  "successMessage": null,
  "data": null,
  "errors": [
    {
      "code": 400,
      "message": "خطا در پردازش اطلاعات: تاریخ و ساعت شروع نباید بعد از تاریخ و ساعت پایان باشد., توضیحات بیشتر:"
    }
  ],
  "warnings": null,
  "meta": {
    "nextAction": "",
    "serverDateTime": "2026-11-03T10:25:00"
  }
}
```

برای فیلدهای اجباری حذف‌شده، مقدار غیرعددی صفحه یا محدودیت‌های مدل، ASP.NET Core می‌تواند پاسخ `ValidationProblemDetails` با `errors` به شکل نگاشت نام فیلد به آرایه پیام‌ها برگرداند. 401 و 403 نیز ممکن است بدنه خالی داشته باشند. بنابراین پردازش خطا نباید وجود envelope یا JSON را برای همه پاسخ‌ها الزامی بداند. ابتدا HTTP status و سپس شکل بدنه را بررسی کنید؛ نمایش متن خام پاسخ غیر JSON مناسب نیست.

## ۸. نمونه TypeScript برای فراخوانی

این مثال مستقل است؛ در پروژه واقعی، هدر توکن و مدیریت خطا را از کلاینت مشترک برنامه بگیرید. `apiBaseUrl` باید Base URL کامل و مطابق تنظیمات همان محیط باشد؛ پیشوندی مثل `/api` را دستی اضافه نکنید.

```ts
type HttpErrorFilters = {
  statusCodeClass: "4XX" | "5XX";
  fromDate: string;
  toDate: string;
  fromTime: string;
  toTime: string;
  page: number;
  pageSize: number;
};

type HttpErrorRow = {
  id: number;
  dateJalali: string;
  time: string;
  statusCode: number;
  requestMethod: string | null;
  routeTemplate: string | null;
  traceId: string | null;
  userId: string | null;
  message: string | null;
};

type SuccessEnvelope<T> = {
  success: true;
  httpStatusCode: 200;
  successMessage: string | null;
  data: T;
  errors: null | { code: number; message: string }[];
  warnings: null | { code: number; message: string }[];
  meta: { nextAction: string; serverDateTime: string };
};

class HttpErrorLogsRequestError extends Error {
  constructor(public status: number, public body: unknown) {
    super(`HTTP ${status}`);
  }
}

async function getHttpErrorLogs(
  apiBaseUrl: string,
  token: string,
  filters: HttpErrorFilters,
  signal?: AbortSignal,
): Promise<HttpErrorRow[]> {
  const base = apiBaseUrl.endsWith("/") ? apiBaseUrl : `${apiBaseUrl}/`;
  const url = new URL("v1/logging/errors", base);
  for (const [key, value] of Object.entries(filters)) {
    url.searchParams.set(key, String(value));
  }

  const response = await fetch(url, {
    method: "GET",
    headers: {
      Authorization: `Bearer ${token}`,
      Accept: "application/json",
    },
    signal,
  });

  // Authentication failures can have an empty body.
  let body: unknown = null;
  try {
    body = await response.json();
  } catch (error) {
    if (signal?.aborted) throw error;
    if (response.ok) throw new Error("پاسخ سرور JSON معتبر نیست.");
  }
  if (!response.ok) {
    throw new HttpErrorLogsRequestError(response.status, body);
  }

  const envelope = body as Partial<SuccessEnvelope<HttpErrorRow[]>> | null;
  if (envelope?.success !== true || !Array.isArray(envelope.data)) {
    throw new Error("ساختار پاسخ دریافت خطاها معتبر نیست.");
  }
  return envelope.data;
}
```

هنگام اعمال فیلتر جدید، درخواست قبلی را با `AbortController` لغو کنید یا پاسخ قدیمی را با شناسه درخواست کنار بگذارید. لغو درخواست نباید به‌عنوان خطا به کاربر نمایش داده شود. اگر کلاینت مشترک برنامه envelope را باز می‌کند، داده را دوباره از `data.data` نخوانید.

## ۹. رفتار صفحه و معیار تحویل

فرم فارسی و RTL شامل «گروه خطا»، «از تاریخ»، «تا تاریخ»، «از ساعت»، «تا ساعت» و دکمه «نمایش خطاها» باشد. فیلترها هنگام فشردن دکمه اعمال شوند؛ جابه‌جایی صفحه از آخرین فیلتر اعمال‌شده استفاده کند. ستون‌های پیشنهادی: تاریخ، ساعت، کد وضعیت، متد، مسیر، شناسه کاربر و شناسه پیگیری؛ متن پیام در جزئیات ردیف قرار بگیرد.

- قبل از جست‌وجوی اول، راهنمای تکمیل فیلترها نمایش داده شود.
- هنگام دریافت داده، وضعیت بارگذاری و جلوگیری از ارسال تکراری وجود داشته باشد.
- «نتیجه خالی»، «خطای دریافت» و «بدون دسترسی» وضعیت‌های جدا باشند.
- کد وضعیت، ساعت، مسیر و شناسه‌ها داخل صفحه RTL به‌صورت خوانا و با جهت LTR نمایش داده شوند.
- تغییر گروه به `5XX`، تاریخ شمسی نامعتبر، بازه معکوس، بازه بیش از ۳۱ روز و اندازه صفحه خارج از محدوده بررسی شوند.
- جست‌وجوی کل روز، جست‌وجوی یک دقیقه و بازه چندروزه شامل شب بررسی شوند.
- نمایش ردیف تاریخی با کد 401 باعث خروج کاربر از نشست فعلی نشود.
- صفحه بعد خالی، فیلدهای null، متن طولانی و رسیدن پاسخ قدیمی پس از پاسخ جدید بررسی شوند.

گزارش فقط درخواست‌های ثبت‌شده با کد وضعیت HTTP را نشان می‌دهد؛ پیام‌های عمومی لاگ بدون کد وضعیت و خطاهای کلاینتی که به سرور نرسیده‌اند در آن نیستند. برای نام کاربر، متن بدنه خطای اصلی، جزئیات exception، نمودار و خروجی فایل، قراردادی در این API تعریف نشده است.
