## حفظ رفتار

بدنهٔ کامل ۲۴۵ متد و ۲۵ بدنهٔ تراکنش با نسخهٔ پیش از ادغام مقایسه می‌شود؛ فرمول‌ها، ثابت‌ها، متن SQL و رشته‌ها، ترتیب فراخوانی‌ها و awaitها در این مقایسه حضور دارند. نگاشت نام متدها و فیلدها در `ServiceConsolidationOperations19.json` ثبت شده است. ۱۶۴ متد مصرف‌کننده نیز از نظر منطق، پارامترها، ویژگی‌های HTTP و مجوزها مقایسه می‌شوند.

وابستگی داخلی عملیات یک سرویس، مانند صدور قبض لحظه‌ای به قبض آزاد، به فراخوانی داخل همان سرویس تبدیل شد. وابستگی‌های مشترک هم‌نوع یکپارچه شدند و تزریق خود سرویس به خودش حذف شد. بررسی DI، پیاده‌سازی و عمر Scoped را کنترل می‌کند.

در بازبینی زنجیرهٔ سازنده‌های واقعی، چرخهٔ `MeterFlowService → MeterReadingDetailSendSmsHandler → MeterFlowService` پیدا شد. وابستگی قبلیِ `ICalculationConfirmationHandler` در هندلر پیامک فقط تزریق شده بود و در هیچ متدی استفاده نمی‌شد؛ پس از تجمیع، همان وابستگی بلااستفاده چرخه ایجاد می‌کرد. فیلد، پارامتر سازنده و دو دستور مربوط به آن حذف شدند. تست ساختاری، بلااستفاده بودن وابستگی و ثابت ماندن تمام بدنه‌ها و رشته‌های پیامک را بررسی می‌کند. تست اجرایی جدید نیز زنجیرهٔ سازنده‌های پیاده‌سازی‌های واقعی را از هر ۱۹ سرویس پیمایش می‌کند تا چرخه پشت وابستگی‌های جایگزین‌شده پنهان نماند.

URLها و روش‌های HTTP حفظ شدند. در کنترلرهای این دسته، پیشوند مسیر در اتریبیوت بالای کنترلر قرار دارد و مسیر اکشن‌ها نسبی است؛ این بررسی، اتریبیوت‌های `HttpGet` و `HttpPost` را نیز پوشش می‌دهد. هفت مسیر BankReceipt با کشف واقعی MVC از نظر URL نهایی، روش HTTP و نبود تداخل بررسی می‌شوند. نام کنترلرها و متادیتای مجوزها حفظ شده‌اند.

هش ۱۰۱ فایل محافظت‌شده، شامل فایل‌های Tariff، قرارداد و پیاده‌سازی `TrackingFlowGetHandler` و نسخهٔ اصلاح‌شدهٔ `RequestRegistrationService`، بررسی می‌شود. TrackingFlow با نسخهٔ Git نیز بدون اختلاف بود.

## اصلاح await درخواست پس از فروش

اصلاح دستی کاربر برای async شدن اعتبارسنجی حفظ شد. فراخوانی `CreateAfterSaleGetMoshtrackCreateDto` در سرویس نیز await شد تا نتیجهٔ Task به DTO تخصیص داده نشود. تست‌های Workflow تأیید می‌کنند که تأخیر اعتبارسنجی جلوی ادامهٔ عملیات را می‌گیرد و خطا یا لغو آن مانع Commit می‌شود. نسخهٔ اصلی snapshot حفظ شده و فقط همین اصلاح مشخص در مقایسهٔ ساختاری مجاز است.

## نتیجهٔ بررسی‌ها

| بررسی | نتیجه |
| --- | --- |
| Build پروژهٔ API | بدون خطا؛ دارای هشدارهای موجود |
| Build پروژهٔ BridgeApi | بدون خطا |
| بررسی ساختاری Operations19 | ۱۹۹۵ کنترل پایه؛ با تطبیق مستقل Git مجموعاً ۲۱۳۵ کنترل؛ ۳۲ کپی SQL و ۶ کپی فرمان Bulk با منبع تطبیق دارند |
| تست اجرایی Operations19 | ۲۴۶۳ کنترل؛ ۸۱ امضای عمومی و overload، ۱۳۴۲ سناریوی قبل/بعد، ۲۴۴ حالت خطا/لغو/انتظار SQL؛ بررسی چرخهٔ سازنده‌ها برای ۱۹ سرویس |
| مسیرهای نمونه | ۷۶ اجرای عادی و ۵ رد شدن صریح توسط اعتبارسنجی کسب‌وکار |
| تست‌های اجرایی چهار دستهٔ قبلی | Critical10، Auxiliary10، Management20 و Workflow10 پاس شدند |
| پنج مجموعهٔ رگرسیون کنترلرها | مجموعاً ۹۵۷۴ کنترل پاس شدند |

کنترل‌های مالی صریح، تبدیل مبلغ ۱۲۳۴۵۶۷ به مبلغ پرداخت ۱۲۳۴۰۰۰ و برابری آن با مبلغ انبار داده، مبلغ و کاربر ثبت هزینه، جمع ۳۵۰۰ برای دو ردیف فایل بانکی، و فرمول مبلغ، بودجه، مالیات و جمع آب تانکری را بررسی می‌کنند. در تزریق خطای SQL به تأیید قرائت، نبود فراخوانی ارسال پیامک بعد از شکست نیز کنترل می‌شود.

پنج مسیر نمونه عمداً به رد کسب‌وکار می‌رسند: برگشت قدیمی‌تر از مهلت، تاریخ قدیمی قبض آزاد، مرحلهٔ نامعتبر جریان، و دو مسیر تأیید قرائت با دادهٔ نمونهٔ نامعتبر. نوع خطای مورد انتظار برای این موارد ثبت شده است؛ برابر بودن دو خطای دلخواه به‌عنوان موفقیت پذیرفته نمی‌شود. این پنج مسیر، اثبات اجرای موفق سناریوی واقعی آن عملیات نیستند.

تست‌ها از فرمان‌های واقعی Dapper با اتصال ضبط‌کننده استفاده می‌کنند. در کپی‌های تست فرمان‌های Bulk، فقط مرز ساخت `SqlBulkCopy` و `SqlCommand` جایگزین شده است؛ SQL، جدول، ستون‌ها، mapping و ردیف‌های تولیدشده حفظ و بررسی می‌شوند. فایل‌های اصلی persistence تغییر نکرده‌اند.

هیچ اتصال واقعی SQL Server، ارسال پیامک، اجرای job یا تغییر آرشیو OpenKM انجام نشده است. بنابراین این نتیجه، تأیید اجرای یکپارچه روی دیتابیس واقعی نیست. ایرادهای قدیمی خارج از محدوده، مانند نبود Commit در ویرایش تاریخ نصب و مدیریت چند اتصال در SubscriptionAssignment، در این ادغام اصلاح نشده‌اند و تست‌های مربوط آن‌ها را صریحاً مشخص می‌کنند.

## اجرای مجدد

از مسیر `D:\Projects\Aban360` در PowerShell:

```powershell
dotnet build Aban360.Api/Aban360.Api.csproj --no-restore -m:1
dotnet build Aban360.BrdigeApi/Aban360.BrdigeApi.csproj --no-restore -m:1
dotnet run --project tests/Aban360.CriticalServiceStructure.RegressionTests --no-restore -- --operations19 --verify-head
dotnet run --project tests/Aban360.MergedControllers.SmokeTests --no-restore -- --operations19
```

تغییرات Commit یا منتشر نشده‌اند.

## بازبینی مستقل پس از نگرانی دربارهٔ قطع اجرا

هر ۷۰ کلاس مبنای قبل از ادغام با نسخهٔ Git تطبیق داده شد؛ فقط تغییر نام وابستگی‌ها و فراخوانی‌های ثبت‌شده در ادغام‌های تأییدشدهٔ قبلی اعمال می‌شوند. در این مقایسه خروجی Git صریحاً با UTF-8 خوانده می‌شود تا متن فارسی در ویندوز مخدوش تفسیر نشود. پایان خط Git و Windows فقط در مقایسهٔ Git با snapshot همسان می‌شود؛ مقایسهٔ SQL و رشته‌های snapshot با سرویس همچنان دقیق است.

هر ۲۱۳۵ کنترل ساختاری و ۲۴۶۳ کنترل اجرایی دوباره پاس شدند. Build جدید API و BridgeApi نیز بدون خطا بود. بررسی ساختاری چهار دستهٔ قبلی با `--verify-head` دوباره پاس شد. در این بازبینی، اختلاف ناخواسته‌ای در کد عملیاتی پیدا نشد و تغییری در کد اجرایی داده نشد؛ ابزار تطبیق مبنا تقویت شد. محدودیت تست با دیتابیس و سرویس‌های جایگزین‌شده همچنان برقرار است.
