# تحویل به Agent فرانت — صفحه پایش درخواست‌های HTTP

## مأموریت و قواعد اجرا

یک صفحه فارسی و RTL برای پایش درخواست‌ها در بخش SystemPool بساز. ساختار پروژه فرانت، مسیرها، کنترل دسترسی، کلاینت HTTP، مدیریت وضعیت، جدول، انتخابگر تاریخ و نمایش خطای موجود را ابتدا بررسی و همان الگوها را استفاده کن. وابستگی، فریمورک یا سرویس بیرونی جدید اضافه نکن؛ محیط مقصد ایزوله است. این سند قرارداد فعلی بک‌اند است؛ قابلیت پشتیبانی‌نشده را به API نسبت نده.

صفحه شامل فیلتر مشترک بازه شمسی، کارت‌های آمار و سه تب «مسیرها»، «کاربران» و «کندترین درخواست‌ها» باشد. داده خلاصه و تب فعال را پس از کلیک «نمایش گزارش» دریافت کن؛ تب‌های دیگر هنگام فعال‌شدن بارگیری شوند. تمام صفحه‌ها از فیلتر اعمال‌شده یکسان استفاده کنند. داده نمونه صرفاً برای تست است و نباید جای پاسخ واقعی نمایش داده شود.

## قرارداد HTTP و دسترسی

همه درخواست‌ها GET و زیر base URL موجود برنامه هستند. احراز هویت با روش فعلی پروژه انجام شود. دسترسی به نقش تنظیم‌شده در `ApiSettings:AdminRoleName` محدود است (مقدار فعلی Admin). مخفی‌کردن منو جای کنترل سمت سرور را نمی‌گیرد.

| مسیر | کاربرد و ترتیب ثابت سمت سرور |
| --- | --- |
| `/v1/logging/http-requests/summary` | یک ردیف آمار کلی؛ حتی برای بازه بدون داده، یک ردیف با مقادیر صفر |
| `/v1/logging/http-requests/routes` | گروه‌بندی برحسب متد و قالب مسیر؛ بیشترین زمان نزولی |
| `/v1/logging/http-requests/users` | گروه‌بندی برحسب شناسه کاربر؛ میانگین زمان نزولی |
| `/v1/logging/http-requests/slowest` | درخواست‌های منفرد؛ مدت زمان نزولی، سپس شناسه داخلی لاگ نزولی |

مرتب‌سازی دلخواه، جست‌وجوی نام کاربر، فیلتر متد یا وضعیت و نمودار سری زمانی فعلاً API ندارند. مرتب‌سازی محلی یک صفحه را به‌عنوان مرتب‌سازی کل داده نمایش نده.

### Query parameters مشترک

| نام | نوع / پیش‌فرض | قاعده |
| --- | --- | --- |
| `FromDate` | string، اجباری | تاریخ شمسی `yyyy/MM/dd` |
| `ToDate` | string، اجباری | تاریخ شمسی `yyyy/MM/dd` |
| `FromTime` | string، `00:00` | `HH:mm`، ساعت ۲۴ ساعته |
| `ToTime` | string، `00:00` | `HH:mm`، ساعت ۲۴ ساعته |
| `UserId` | string، اختیاری | تطبیق دقیق شناسه؛ پارامتر خالی را ارسال نکن |
| `RouteTemplate` | string، اختیاری | تطبیق دقیق قالب مسیر؛ مثلاً `/users/{id}` |
| `Page` | integer، 1 | حداقل 1؛ برای summary نادیده گرفته می‌شود |
| `PageSize` | integer، 50 | از 1 تا 200؛ برای summary نادیده گرفته می‌شود |

بازه به‌شکل **شروع شامل و پایان غیرشامل** است. پایان باید بزرگ‌تر از شروع باشد؛ طول بازه حداکثر ۳۱ روز است. ارقام فارسی و عربی پذیرفته می‌شوند؛ ارسال ارقام لاتین توصیه می‌شود. برای «کل روز ۱۴۰۵/۰۸/۰۱»، شروع را `1405/08/01 00:00` و پایان را `1405/08/02 00:00` ارسال کن. افزایش روز با ابزار تقویم معتبر موجود انجام شود؛ رشته تاریخ را دستی جمع نکن. اگر انتخابگر پایان را شامل نمایش می‌دهد، تبدیل به پایان غیرشامل را فقط یک بار انجام بده.

مثال (URL را با URLSearchParams یا ابزار مشابه موجود بساز):

```http
GET /v1/logging/http-requests/users?FromDate=1405%2F08%2F01&ToDate=1405%2F08%2F02&Page=1&PageSize=50
```

## ساختار پاسخ موفق

نام‌گذاری JSON بر اساس پیش‌فرض ASP.NET Core، camelCase است. `data` در **هر چهار endpoint آرایه** است؛ خلاصه را از `data[0]` بخوان. خروجی در envelope فعلی برنامه قرار دارد:

```json
{
  "success": true,
  "httpStatusCode": 200,
  "successMessage": "...",
  "data": [
    {
      "totalGroups": 1,
      "requestMethod": null,
      "routeTemplate": null,
      "userId": null,
      "traceId": null,
      "timeStamp": null,
      "statusCode": null,
      "requestCount": 120,
      "serverErrorCount": 3,
      "averageMilliseconds": 145.5,
      "maximumMilliseconds": 2410.2,
      "totalMilliseconds": 17460
    }
  ],
  "errors": null,
  "warnings": null,
  "meta": {}
}
```

نمونه بالا شماتیک است؛ فیلدهای `meta` را با مدل موجود پروژه بخوان، نه با فرض خالی‌بودن آن.

### معنای فیلدها و نمایش

| فیلد | معنا |
| --- | --- |
| `requestCount` | تعداد رویدادهای ثبت‌شده؛ در slowest برابر 1 |
| `serverErrorCount` | تعداد پاسخ‌های 500 به بالا؛ 499 خطای سرور نیست |
| `averageMilliseconds` | میانگین زمان پردازش؛ در slowest مدت همان درخواست |
| `maximumMilliseconds` | بیشترین زمان؛ در slowest مدت همان درخواست |
| `totalMilliseconds` | مجموع زمان درخواست‌ها؛ زمان هم‌پوشان درخواست‌های هم‌زمان نیز جمع می‌شود |
| `totalGroups` | تعداد کل ردیف‌های گزارش قبل از صفحه‌بندی؛ روی هر ردیف تکرار می‌شود |
| `requestMethod`, `routeTemplate` | در routes و slowest مقدار دارند |
| `userId` | در users و slowest؛ null یعنی ناشناس، نه کاربر حذف‌شده |
| `traceId` | فقط slowest؛ امکان کپی فراهم کن، لینک جزئیات بدون API نساز |
| `timeStamp` | فقط slowest؛ رشته DateTime میلادی بدون قرارداد offset قطعی |
| `statusCode` | فقط slowest؛ شامل 499 داخلی برای لغو درخواستی که به middleware رسیده |

ستون‌های نامرتبط هر endpoint ممکن است null یا صفر باشند؛ آن‌ها را به‌عنوان داده معنادار نمایش نده. `userId` و `traceId` رشته‌اند. نام کاربر از این API برنمی‌گردد؛ نام ساختگی یا درخواست جداگانه برای هر ردیف نساز. درخواست ناشناس در فیلتر اختصاصی فعلاً قابل انتخاب نیست؛ حذف UserId یعنی همه کاربران.

کارت‌ها: تعداد درخواست، میانگین زمان، بیشترین زمان و تعداد خطای سرور. نرخ خطا در فرانت از `serverErrorCount / requestCount * 100` محاسبه شود؛ برای تعداد صفر، صفر نمایش بده. میانگین کل را از summary بگیر؛ میانگین ساده میانگین کاربران یا مسیرها نادرست است.

تب مسیرها: متد، قالب مسیر، تعداد، میانگین، بیشترین زمان و خطاهای سرور.
تب کاربران: شناسه/ناشناس، تعداد، میانگین، بیشترین زمان و خطاهای سرور.
تب کندترین‌ها: زمان، متد، قالب مسیر، وضعیت، مدت، شناسه کاربر و TraceId قابل کپی.
ستون‌های مسیر و شناسه با جهت LTR و متن به‌صورت امن (بدون HTML خام) نمایش داده شوند.

مدت‌ها میلی‌ثانیه هستند؛ نمایش گرد‌شده مجاز است، مقدار اصلی برای محاسبه حفظ شود. آستانه Warning در لاگ قابل تنظیم است و توسط این API برنمی‌گردد؛ از رنگ‌بندی مبتنی بر فرض ثابت ۲ ثانیه استفاده نکن.

## صفحه‌بندی، بارگیری و خطا

- برای هر تب Page مستقل نگه دار؛ با تغییر فیلتر یا اندازه صفحه، Page را 1 کن.
- تعداد کل از `data[0].totalGroups` خوانده می‌شود. صفحه خالی `[]` است و total ندارد؛ نبود total را با صفر قطعی کل گزارش اشتباه نگیر. اگر صفحه بعد خالی بود، امکان برگشت حفظ شود.
- درخواست قدیمی با تغییر فیلتر لغو یا پاسخ دیررس آن نادیده گرفته شود. داده و کارت‌های دو بازه مختلف با هم نمایش داده نشوند. خطای یک تب کل صفحه را از بین نبرد.
- حالت loading، بدون داده، خطا و تلاش مجدد مستقل داشته باش. نبود داده را صفر برای تمام تب‌ها فرض نکن.
- 401: جریان ورود/تمدید نشست موجود؛ 403: عدم دسترسی؛ 400: خطای ورودی؛ 5xx یا خطای شبکه: پیام عمومی و تلاش مجدد.
- شکل پاسخ 400 ممکن است envelope خطای برنامه یا ValidationProblemDetails خود ASP.NET باشد؛ کلاینت باید هر دو را با الگوی موجود مدیریت کند. 401/403 الزاماً بدنه JSON ندارند.
- auto-refresh پیش‌فرض خاموش باشد؛ دریافت دستی و بارگیری تنبل تب‌ها فشار پرس‌وجوی XML را کم می‌کند.

## محدودیت‌هایی که باید به کاربر توضیح داده شوند

متن راهنما: «زمان‌ها مربوط به پردازش سمت سرور هستند و زمان شبکه و مرورگر را شامل نمی‌شوند. آمار بر اساس لاگ‌های ذخیره‌شده و موجود محاسبه می‌شود.»

گزارش همه ترافیک وب‌سرور نیست: فایل‌های ثابت، health probeها و درخواست‌های پاسخ‌گرفته پیش از middleware ثبت نمی‌شوند. داده قبل از فعال‌شدن قابلیت، داده حذف‌شده یا لاگ ذخیره‌نشده قابل شمارش نیست. ذخیره دسته‌ای SQL ممکن است نمایش آخرین درخواست‌ها را کمی به تأخیر بیندازد. فراخوانی همین APIهای گزارش نیز درخواست HTTP است و در گزارش‌های بعدی وارد آمار می‌شود.

مرز تاریخ فعلاً مطابق ساعت ثبت‌شده سرور است، نه منطقه زمانی مرورگر؛ timestamp بدون offset را خودکار UTC فرض نکن. پیش از تحویل نهایی، قرارداد منطقه زمانی را با بک‌اند و سرور مقصد تأیید کن.

## معیار پذیرش برای Agent

1. استفاده از الگوها و اجزای موجود فرانت؛ فارسی و RTL، بدون وابستگی اینترنتی جدید.
2. تطبیق فیلتر هر چهار API، بازنشانی صفحه و جلوگیری از پاسخ‌های قدیمی.
3. تست روز کامل، پایان ماه/سال شمسی، ورودی نامعتبر و بازه بیش از ۳۱ روز.
4. تست خلاصه صفر، کاربر ناشناس، صفحه خالی، مقادیر null و خطاهای 400/401/403/500.
5. نمایش درست مدت درخواست منفرد و میانگین کاربران؛ عدم میانگین‌گیری مجدد از میانگین‌ها.
6. تست دسترسی و درخواست واقعی روی محیط متصل به SQL؛ تست فعلی بک‌اند شامل اجرای SQL واقعی نیست.
7. در پایان، فایل‌های تغییرکرده، نتیجه تست‌ها و محدودیت‌های باقی‌مانده را گزارش کن. API یا فیلتر جدیدی را بدون هماهنگی اختراع نکن.
