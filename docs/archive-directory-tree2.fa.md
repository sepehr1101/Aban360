# فهرست بایگانی همراه عنوان فایل

## درخواست

```http
GET {apiBaseUrl}/v1/open-km/directory-tree2?input={billId}&trackNumber={trackNumber}
Authorization: Bearer {accessToken}
```

`input` همان ورودی مسیر قبلی `directory-tree` است. `trackNumber` اختیاری است و مانند مسیر قبلی به handler موجود فرستاده می‌شود. آدرس پایه و پیشوند میزبانی را از تنظیمات فعلی فرانت بگیرید.

## مسیرهای دیگر در همان کنترلر

هر چهار مسیر در `GetDirectoryTree2Controller` قرار دارند و پاسخ همه شامل `data.document[].fileTitle` است:

| نسخه قبلی | نسخه دارای عنوان | نوع درخواست و ورودی |
| --- | --- | --- |
| `directory-tree` | `directory-tree2` | `GET` با `input` و `trackNumber` اختیاری |
| `discount-directory-tree` | `discount-directory-tree2` | `GET` با `input` همان مسیر قبلی |
| `request-directory-tree` | `request-directory-tree2` | `GET` با `input` همان شماره پیگیری قبلی |
| `removed-directory-tree` | `removed-directory-tree2` | `POST` با همان بدنه JSON قبلی |

پیشوند همه مسیرها `{apiBaseUrl}/v1/open-km/` است. بدنه درخواست فایل‌های حذف‌شده:

```json
{
  "folderName": "شناسه قبض یا شماره پیگیری",
  "isBillId": true
}
```

برای پوشه قبض، `isBillId` برابر `true` و برای پوشه پیگیری برابر `false` است. در حالت پیگیری، شماره خام و بدون پیشوند `r_` فرستاده شود؛ handler قبلی خودش پیشوند را اضافه می‌کند. بدنه بدون تغییر به همان handler قبلی منتقل می‌شود.

## پاسخ

پاسخ در envelope معمول API قرار می‌گیرد. آرایه فایل‌ها همچنان `data.document` است؛ هر فایل تمام مشخصات قبلی را همراه با فیلد تازه `fileTitle` دارد. مثال زیر فقط چند فیلد پاسخ را نشان می‌دهد:

```json
{
  "success": true,
  "httpStatusCode": 200,
  "data": {
    "document": [
      {
        "uuid": "document-uuid",
        "title": "scan.jpg",
        "mimeType": "image/jpeg",
        "fileTitle": "سند مالکیت"
      }
    ]
  }
}
```

`title` همان نام/عنوان فعلی فایل است و جایگزین نمی‌شود. `fileTitle` عنوان ترجمه‌شده metadata است؛ همان مفهومی که از مسیر `file-title` دریافت می‌شد.

## تغییر فرانت

1. در صفحه‌ای که به نسخه جدید منتقل می‌شود، به‌جای `directory-tree`، مسیر `directory-tree2` فراخوانی شود.
2. عنوان نمایشی از `document.fileTitle` خوانده شود؛ فراخوانی جداگانه `file-title` برای هر فایل حذف شود.
3. برای دریافت تصویر، همان مسیر فعلی `document-binary` با همان UUID و پارامترهای قبلی استفاده شود. این API جدید، binary یا base64 تصویر را در فهرست قرار نمی‌دهد.
4. اگر `fileTitle` خالی بود، فرانت می‌تواند `title` را به‌عنوان نام جایگزین نمایش دهد. خالی‌بودن ممکن است ناشی از نبود metadata عنوان یا خطای دریافت metadata همان فایل باشد؛ فایل از فهرست حذف نمی‌شود.

برای هشت فایل، تعداد درخواست‌های فرانت برای این کار از ۱۷ به ۹ کاهش می‌یابد: یک فهرست و هشت binary. درخواست‌های مستقل SignalR در این شمارش نیستند.

## رفتار بک‌اند و سازگاری

- مسیر جدید، handler فعلی فهرست را یک‌بار فراخوانی می‌کند؛ ورودی، trackNumber، کاربر و توکن لغو همان‌طور منتقل می‌شوند.
- اطلاعات مرجع metadata یک‌بار برای کل فهرست خوانده می‌شود. اگر خواندن این مرجع شکست بخورد، فایل‌ها با عنوان خالی برمی‌گردند و خطا ثبت می‌شود؛ مانند نسخه قبلی، نمایش اصل فهرست به جدول عنوان‌ها وابسته نیست. خطای دریافت فهرست اصلی همچنان به همان شکل قبلی برگردانده می‌شود.
- metadata فایل‌ها با حداکثر چهار درخواست هم‌زمان دریافت می‌شود؛ UUID تکراری فقط یک‌بار خوانده می‌شود و ترتیب فایل‌ها حفظ می‌شود.
- خطا یا timeout دریافت عنوان یک فایل در لاگ ثبت می‌شود و فقط عنوان همان فایل خالی می‌ماند. لغو درخواست کاربر به‌عنوان خطای عنوان پنهان نمی‌شود.
- عنوانی که فقط از فاصله تشکیل شده باشد، مطابق رفتار `file-title` قبلی به رشته خالی تبدیل می‌شود.
- این تجمیع تعداد درخواست‌های فرانت را کم می‌کند؛ سرویس OpenKM فعلی همچنان برای metadata هر UUID، درخواست جداگانه دریافت می‌کند.
- پاسخ نسخه جدید پس از تکمیل تلاش برای دریافت عنوان‌ها آماده می‌شود؛ زمان پاسخ خودِ فهرست لزوماً برابر نسخه قبلی نیست و باید روی بایگانی واقعی اندازه‌گیری شود.
- هر مسیر فهرست، handler قبلی مربوط به همان نوع بایگانی را اجرا می‌کند؛ سپس سرویس مشترک `IArchiveFileTitleEnricher` عنوان‌ها را تکمیل می‌کند.
- هر چهار مسیر فهرست قدیمی، `file-title` و `document-binary`، DTOهای قبلی و پیاده‌سازی‌های قبلی تغییر نکرده‌اند. فرانت قبلی نیازی به مهاجرت فوری ندارد.
- این تغییر به اسکریپت دیتابیس یا تنظیمات جدید نیاز ندارد.

## آزمون

```powershell
dotnet run --project tests/Aban360.ArchiveDirectory.SmokeTests/Aban360.ArchiveDirectory.SmokeTests.csproj
dotnet run --project tests/Aban360.OpenKm.SmokeTests/Aban360.OpenKm.SmokeTests.csproj
```

آزمون جدید، ثبت سرویس، انتقال ورودی‌ها، یک‌بار خواندن مرجع، سقف هم‌زمانی، حذف فراخوانی تکراری UUID، ترجمه عنوان، خطای جزئی و timeout، حفظ ترتیب و تمام مشخصات قبلی، تغییرنکردن JSON قدیمی، مسیر جدید و قدیم، فهرست خالی و لغو درخواست را بررسی می‌کند. آزمون‌ها از سرویس‌های شبیه‌سازی‌شده استفاده می‌کنند و به بایگانی اصلی درخواست نمی‌فرستند.

نتیجه نهایی: ساخت API بدون خطا انجام شد؛ هر ۴۸ بررسی مسیرهای جدید و هر ۴۲ بررسی موجود OpenKM موفق بودند. علاوه بر قرارداد مسیر، نوع HTTP، بدنه JSON، انتقال ورودی‌ها و دریافت عنوان، انتخاب پوشه‌ها با handlerهای موجود تخفیف، درخواست و حذف‌شده در هر دو حالت قبض و پیگیری مقایسه شد. تمام فیلدها و ترتیب تمام فایل‌ها با خروجی قبلی تطبیق داده شد. خطای جدول عنوان‌ها دیگر نمایش فهرست را متوقف نمی‌کند و عنوان فقط از فاصله نیز مثل `file-title` قبلی خالی می‌شود. فایل‌های پیاده‌سازی و DTOهای مسیرهای قبلی تغییری نکرده‌اند. این بررسی با OpenKM شبیه‌سازی‌شده انجام شد؛ زمان پاسخ و اتصال بایگانی اصلی در محیط عملیاتی سنجیده نشده است.
