# راهنمای پیاده‌سازی فرانت تیکتینگ Aban360

مخاطب: برنامه‌نویس React یا AI Agent مسئول توسعه رابط کاربری.

آخرین بازبینی: ۲۰۲۶/۱۰/۲۷. برای شروع تحویل، فایل
[START_HERE.fa.md](START_HERE.fa.md) را هم بخوانید.
طبق اعلام مالک پروژه، اسکریپت ایجاد جداول روی سرور با موفقیت اجرا شده است.
تست کامل APIهای منتشرشده، آپلود/دریافت فایل و دسترسی کاربران روی همان سرور
هنوز گزارش نشده است؛ نصب موفق جداول را معادل تأیید همه این مراحل نگیرید.

این سند قرارداد **کد فعلی** است. راهنمای کوتاه API در
[README کنترلرها](../../Aban360.Api/Controllers/V1/UserPool/Ticketing/README.md)
و دستور کار آماده Agent در [FRONTEND_AGENT_PROMPT.fa.md](FRONTEND_AGENT_PROMPT.fa.md) قرار دارد.

## ۱. کلیت قابلیت

کاربر تیکتی با عنوان و یک پیام اولیه ایجاد می‌کند. هر پیام می‌تواند متن، عکس، فیلم
یا ترکیبی از آن‌ها داشته باشد. مدیر تیکت را به مسئول پاسخ‌گویی ارجاع می‌دهد.
کاربر و مسئول در همان تیکت گفتگو می‌کنند. کاربر به **هر پاسخ مسئول** یک امتیاز
۱ تا ۵ می‌دهد و می‌تواند امتیاز خودش را ویرایش کند. گزارش، تعداد تیکت‌ها، تعداد
امتیازهای ثبت‌شده و میانگین آن‌ها را نمایش می‌دهد.

روابط داده‌ها:

```text
Ticket
  └─ TicketMessage[]
       ├─ TicketAttachment[]
       └─ TicketRating?   ← حداکثر یک امتیاز برای هر پیام
```

متن اولیه هم یک `TicketMessage` است؛ داخل `Ticket` فیلد متن وجود ندارد.
فایل‌ها در SQL Server با FILESTREAM نگهداری می‌شوند. فرانت فقط با API کار می‌کند
و به مسیر ذخیره‌سازی یا دیتابیس دسترسی مستقیم ندارد.

## ۲. محدوده فعلی

قابلیت‌های موجود: تیکت، گفتگو، پیوست، ارجاع، تغییر وضعیت، امتیاز و گزارش.

در قرارداد فعلی، دسته‌بندی، اولویت، SLA، حذف پیام/فایل/تیکت، اعلان، پیام خوانده‌شده،
جستجوی متن پیام‌ها، پاسخ آماده و بروزرسانی زنده مخصوص تیکتینگ وجود ندارد.
دکمه و مسیر API فرضی برای این امکانات نسازید. متن پیام فعلاً متن ساده است.

## ۳. ورود، دسترسی و نقش‌ها

از سیستم ورود، کاربر جاری و API client موجود در پروژه React استفاده کنید.
ورود یا محل ذخیره توکن جدید نسازید. تمام APIهای این بخش، حتی وضعیت‌ها و فایل‌ها،
نیازمند احراز هویت فعلی پروژه هستند؛ برای Bearer درخواست شامل این هدر است:

```http
Authorization: Bearer <access-token>
```

`userId`، `senderUserId` و `ratedByUserId` را از فرم ارسال نکنید؛ بک‌اند آن‌ها را
از هویت جاری تعیین می‌کند. برای نمایش نقش از اطلاعات معتبر سیستم ورود استفاده کنید؛
بک‌اند مدیر را با نقش `admin` تشخیص می‌دهد.

| عملیات | ثبت‌کننده تیکت | مسئول فعلی تیکت | مدیر |
|---|---|---|---|
| خواندن تیکت، گفتگو، پیوست و امتیاز | بله | بله | بله |
| ارسال پیام در تیکت باز | بله | بله | بله |
| ویرایش متن/پیوست یک پیام | فقط پیام خودش | فقط پیام خودش | فقط پیام خودش |
| تغییر عنوان یا وضعیت تیکت، بستن و بازگشایی | خیر، مگر مسئول یا مدیر باشد | بله | بله |
| تغییر مسئول یا لغو ارجاع | خیر | خیر | بله |
| ثبت امتیاز به پاسخ دیگران | بله | فقط اگر خودش ثبت‌کننده تیکت باشد | فقط اگر خودش ثبت‌کننده تیکت باشد |
| ویرایش امتیاز | فقط امتیاز خودش روی تیکت خودش | همان قاعده | همان قاعده |

روی تیکت بسته، ایجاد پیام و ایجاد/ویرایش پیوست و ویرایش متن مجاز نیست.
ثبت و ویرایش امتیاز روی پاسخ قبلی در تیکت بسته همچنان مجاز است.
مالک تیکت نمی‌تواند پیام خودش را امتیاز بدهد.
پنهان‌کردن دکمه‌ها صرفاً رفتار رابط است؛ تصمیم نهایی همیشه با سرور است.

## ۴. صفحات و اجزای پیشنهادی

داخل پروژه React فعلی و با کامپوننت‌ها، مسیریابی، استایل و مدیریت داده موجود بسازید:

1. **تیکت‌های من:** شماره، عنوان، وضعیت، زمان ایجاد و آخرین فعالیت، جستجو و صفحه‌بندی.
2. **تیکت‌های ارجاع‌شده به من:** همان فهرست با فیلتر مسئول جاری.
3. **مدیریت تیکت‌ها:** برای مدیر؛ صف همه تیکت‌ها، فیلتر کاربر/مسئول و ارجاع.
4. **ثبت تیکت:** عنوان، متن، انتخاب حداکثر پنج فایل و پیش‌نمایش انتخاب‌ها.
5. **جزئیات و گفتگو:** مشخصات تیکت، پیام‌ها، پیوست‌ها، امتیاز هر پاسخ و فرم پاسخ.
6. **گزارش:** تعداد تیکت، تعداد امتیاز، میانگین و تعداد به تفکیک وضعیت با فیلتر تاریخ.

مسیرهای صفحات React را با الگوی پروژه موجود تعیین کنید؛ مسیر API را به‌جای مسیر صفحه استفاده نکنید.
رابط فارسی و RTL باشد و در موبایل هم قابل استفاده بماند.

## ۵. وضعیت‌ها و تغییرات خودکار

مرجع نمایش عنوان، پاسخ `GET /v1/ticket-status/list` است. مقادیر اولیه:

| id | code | title |
|---|---|---|
| 1 | `New` | جدید |
| 2 | `InProgress` | در حال بررسی |
| 3 | `Answered` | پاسخ داده‌شده |
| 4 | `Closed` | بسته‌شده |

ثبت تیکت وضعیت ۱ می‌سازد. ارسال پیام توسط مالک، وضعیت را ۲ می‌کند؛ پاسخ فرد دیگری
که دسترسی دارد، وضعیت را ۳ می‌کند. بعد از ارسال پیام، مشخصات تیکت را دوباره بخوانید.
بستن، `closedAt` را ثبت می‌کند؛ بازگشایی آن را خالی می‌کند.
فهرست تیکت‌ها بر اساس `createdAt` نزولی است، نه آخرین فعالیت؛ پاسخ جدید الزاماً
تیکت را به ابتدای فهرست نمی‌آورد. پیام‌ها از قدیمی به جدید مرتب‌اند.

## ۶. قرارداد عمومی پاسخ و خطا

پاسخ موفق JSON در `data` قرار دارد، نه در ریشه:

```json
{
  "success": true,
  "httpStatusCode": 200,
  "successMessage": "...",
  "data": true,
  "errors": null,
  "warnings": null,
  "meta": {}
}
```

شکل `meta` را برای صفحه‌بندی استفاده نکنید؛ اطلاعات صفحه داخل `data` است.
`data: null` برای پاسخ بدون امتیاز یک نتیجه معتبر است؛ آن را خطا حساب نکنید.

| وضعیت HTTP | رفتار فرانت |
|---|---|
| 200 | بازکردن envelope برای JSON؛ دریافت Blob برای فایل |
| 206 | محتوای بخشی از فایل، نه JSON |
| 400 | اعتبارسنجی یا خطای دامنه؛ نمایش پیام مناسب و حفظ فرم |
| 401 | اجرای جریان تمدید نشست/ورود موجود؛ پاسخ ممکن است بدنه JSON نداشته باشد |
| 403 | عدم اجازه؛ جریان خطای مجوز موجود |
| 413 | فایل/درخواست بزرگ‌تر از حد میزبان؛ ممکن است پاسخ HTML یا متن باشد |
| 415 | فرمت درخواست نادرست؛ مثلاً JSON به مسیر multipart |
| 416 | بازه نامعتبر در درخواست فایل |
| 500 | پیام عمومی قابل فهم؛ جزئیات داخلی سرور را به کاربر نمایش ندهید |

خطای دامنه عموماً envelope با `errors: [{ code, message }]` دارد. اعتبارسنجی خود
ASP.NET ممکن است `ProblemDetails` با `errors: { field: [message] }` برگرداند.
برای همه پاسخ‌ها JSON بودن را فرض نکنید. در کد فعلی، شناسه ناموجود یا عدم دسترسی
به تیکت ممکن است **۴۰۰** برگرداند؛ فقط منتظر ۴۰۴ یا ۴۰۳ نباشید.
درخواست‌های ثبت/ویرایش را بدون اقدام کاربر خودکار تکرار نکنید؛ کلید idempotency ندارند.

## ۷. نوع داده‌های خروجی برای TypeScript

این typeها نام فیلدهای واقعی JSON را نشان می‌دهند؛ با الگوی typeهای پروژه ادغام کنید:

```ts
type Id = number;
type Guid = string;
type ApiDate = string;

interface Ticket {
  id: Id;
  ticketNumber: string;
  subject: string;
  createdByUserId: Guid;
  assignedToUserId: Guid | null;
  statusId: number;
  createdAt: ApiDate;
  updatedAt: ApiDate;
  closedAt: ApiDate | null;
}

interface TicketMessage {
  id: Id;
  ticketId: Id;
  senderUserId: Guid;
  body: string | null;
  createdAt: ApiDate;
}

interface AttachmentInfo {
  id: Id;
  ticketMessageId: Id;
  originalFileName: string;
  contentType: string;
  sizeBytes: number;
  createdAt: ApiDate;
}

interface TicketRating {
  id: Id;
  ticketMessageId: Id;
  ratedByUserId: Guid;
  score: number;
  comment: string | null;
  createdAt: ApiDate;
}

interface TicketStatus { id: number; code: string; title: string }
interface Page<T> { items: T[]; totalCount: number; pageNumber: number; pageSize: number }
interface TicketReport {
  ticketCount: number;
  ratingCount: number;
  averageScore: number | null;
  statusCounts: { statusId: number; count: number }[];
}

interface TicketSearch {
  createdByUserId?: Guid;
  assignedToUserId?: Guid;
  statusId?: number;
  searchText?: string;
  fromDate?: string;
  toDateExclusive?: string;
  pageNumber?: number;
  pageSize?: number;
}

// ورودی مسیر my-list؛ مالک و مسئول از فرانت قابل تعیین نیستند.
type TicketMySearch = Omit<TicketSearch, "createdByUserId" | "assignedToUserId">;
```

شناسه‌های دیتابیس `bigint` هستند و فعلاً به‌صورت JSON number ارسال می‌شوند؛
قرارداد رشته‌ای برای آن‌ها اختراع نکنید. مقادیر فراتر از `Number.MAX_SAFE_INTEGER`
نیازمند تغییر هماهنگ قرارداد بک‌اند و فرانت خواهند بود.
خروجی‌ها نام کامل فرستنده/مسئول را ندارند؛ از lookup موجود کاربران استفاده کنید
یا برچسب «کاربر» و «پشتیبانی» نمایش بدهید. آبجکت `User` یا اطلاعات ورود دریافت نمی‌شود.

## ۸. فهرست، صف مسئول و صفحه‌بندی

`POST /v1/ticket/list` با JSON از نوع `TicketSearch`؛ ارسال `{}` هم معتبر است.
همه فیلترها با AND ترکیب می‌شوند. `searchText` روی **عنوان و شماره تیکت** جستجو می‌کند.

```json
{
  "searchText": "فشار آب",
  "statusId": 1,
  "pageNumber": 1,
  "pageSize": 20
}
```

- فهرست «تیکت‌های من»: از `POST /v1/ticket/my-list` استفاده کنید. بدنه `{}` یا فیلترهای
  `statusId`، `searchText`، تاریخ و صفحه‌بندی را بفرستید. این مسیر برای مدیر هم فقط
  تیکت‌های ثبت‌شده توسط خودش را برمی‌گرداند؛ فیلتر مالک/مسئول ندارد. بدون فیلتر وضعیت،
  همه وضعیت‌ها برگردانده می‌شوند؛ برای دریافت کل نتایج، همه صفحات را بخوانید.
- صف «ارجاع‌شده به من»: `assignedToUserId: currentUser.userId` ارسال کنید.
- مدیر: می‌تواند همه تیکت‌ها یا فیلتر مالک/مسئول را دریافت کند.
- این فیلترها صف ترکیبی «مال من یا ارجاع‌شده به من» نمی‌سازند؛ دو تب مجزا بسازید.
- فیلتر «بدون مسئول» در API فعلی وجود ندارد؛ `null` به معنی فقط تیکت‌های بدون مسئول نیست.
- شماره صفحه از ۱، اندازه پیش‌فرض ۲۰ و حداکثر ۱۰۰ است.
- تعداد صفحات `Math.ceil(totalCount / pageSize)` است. با تغییر فیلتر، صفحه را ۱ کنید.
- جستجو را debounce کنید و درخواست قدیمی را لغو کنید تا پاسخ قدیمی، پاسخ جدید را جایگزین نکند.

## ۹. ثبت تیکت و یافتن شناسه آن

`POST /v1/ticket/create` فقط `multipart/form-data` می‌گیرد:

| نام فیلد | قرارداد |
|---|---|
| `Subject` | الزامی؛ متن غیرخالی، حداکثر ۲۵۵ کاراکتر |
| `Body` | اختیاری؛ حداکثر ۱۰٬۰۰۰ کاراکتر |
| `Attachments` | فایل اختیاری؛ برای هر فایل همین کلید را تکرار کنید |

حداقل متن غیرسفید یا یک فایل لازم است. ذخیره تیکت، پیام اولیه و پیوست‌ها در همین
درخواست انجام می‌شود؛ بعداً دوباره پیام اولیه را به API پیام نفرستید.

```ts
const form = new FormData();
form.append("Subject", subject.trim());
if (body.trim()) form.append("Body", body);
files.forEach(file => form.append("Attachments", file, file.name));
// از client موجود استفاده کنید؛ Content-Type را دستی ست نکنید.
const ticketNumber = await ticketingRequest<string>("/v1/ticket/create", "POST", form);
```

پاسخ `data` یک **رشته شماره تیکت** است؛ نه شناسه عددی و نه آبجکت Ticket.
برای رفتن به صفحه جزئیات، `POST /v1/ticket/list` با `searchText: ticketNumber`
و `pageSize: 100` بفرستید و رکوردی که `ticketNumber` آن دقیقاً برابر است انتخاب کنید.
از `items[0]` بدون بررسی تطابق استفاده نکنید. اگر نتیجه پیدا نشد، شماره پیگیری را
نمایش بدهید و کاربر را به فهرست ببرید؛ ثبت را خودکار دوباره نفرستید.

## ۱۰. بارگیری و نمایش گفتگو

1. `GET /v1/ticket/read/{id}` برای مشخصات تیکت.
2. `POST /v1/ticket-message/list` با `{ ticketId, pageNumber: 1, pageSize: 20 }` برای پیام‌ها.
3. برای هر پیام قابل مشاهده، `GET /v1/ticket-attachment/list/{messageId}` برای پیوست‌ها.
4. برای پاسخ‌های غیرمالک، `GET /v1/ticket-rating/read-by-message/{messageId}` برای امتیاز.

پیام‌ها آبجکت پیوست یا امتیاز توکار ندارند. هر صفحه فقط بخشی از گفتگو است؛
برای آخرین صفحه از `totalCount` استفاده کنید. در اولین ورود می‌توانید آخرین صفحه
را دریافت کنید؛ پیام‌ها را با `id` ادغام کنید تا پس از refresh تکراری نشوند.
پس از ارسال پیام، تعداد صفحات ممکن است تغییر کند؛ آخرین صفحه را دوباره تعیین کنید.

پیام خود کاربر را با `senderUserId === currentUser.userId` مشخص کنید.
تشخیص مالک تیکت با `senderUserId === ticket.createdByUserId` است؛ این دو مفهوم یکی نیستند.
برای مقایسه GUIDها، حروف دو طرف را یکسان کنید؛ مثلاً هر دو را lowercase کنید.
متن را به‌صورت escaped و با حفظ شکست خط نمایش بدهید، مثلاً `white-space: pre-wrap`.
متن کاربر را با `dangerouslySetInnerHTML` نمایش ندهید.
بارگیری پیوست/امتیاز هر پیام حالت loading/error مستقل داشته باشد؛ شکست یک درخواست
نباید کل گفتگو را خالی کند. تعداد درخواست‌های هم‌زمان و پیش‌بارگیری را محدود کنید.

## ۱۱. ارسال و ویرایش پیام

`POST /v1/ticket-message/create` با multipart:

```ts
const form = new FormData();
form.append("TicketId", String(ticketId));
if (body.trim()) form.append("Body", body);
files.forEach(file => form.append("Attachments", file, file.name));
await ticketingRequest<boolean>("/v1/ticket-message/create", "POST", form);
```

پاسخ `data: true` است؛ پیام تازه را دوباره بخوانید. هنگام ارسال، دکمه را غیرفعال کنید.
فقط پس از موفقیت فرم را پاک کنید. خطا، متن و فایل‌های انتخابی را حفظ کند.
در تیکت بسته، فرم پاسخ غیرفعال و دلیل آن مشخص باشد.

ویرایش متن: `POST` یا `PATCH /v1/ticket-message/update` با JSON:

```json
{ "id": 25, "body": "متن اصلاح‌شده" }
```

فقط ارسال‌کننده می‌تواند ویرایش کند. خالی‌کردن متن تنها وقتی مجاز است که پیام پیوست
داشته باشد. `createdAt` زمان ایجاد است و با ویرایش تغییر نمی‌کند؛ فیلد تاریخ ویرایش پیام نداریم.

## ۱۲. پیوست: انتخاب، افزودن، جایگزینی و نمایش

حداکثر **۵ فایل در هر پیام** و **۵۰ MiB = 52,428,800 بایت برای هر فایل**.
فایل صفر بایتی مجاز نیست. اعتبارسنجی کلاینت برای تجربه بهتر است؛ سرور هم بررسی می‌کند.

| نوع | MIME | پسوند |
|---|---|---|
| JPEG | `image/jpeg` | `.jpg`, `.jpeg` |
| PNG | `image/png` | `.png` |
| GIF | `image/gif` | `.gif` |
| WebP | `image/webp` | `.webp` |
| MP4 | `video/mp4` | `.mp4` |
| WebM | `video/webm` | `.webm` |

نام، MIME، پسوند و امضای ابتدایی فایل بررسی می‌شود. HEIC و MOV در قرارداد فعلی
پذیرفته نمی‌شوند. اگر `File.type` خالی است، صرفاً برای ارسال می‌توان MIME متناظر
با پسوند مجاز را روی Blob تعیین کرد؛ این کار محتوا یا فرمت فایل را تبدیل نمی‌کند
و تأیید نهایی همچنان با سرور است. قابلیت پخش واقعی به codec مرورگر هم بستگی دارد؛
اگر پخش ممکن نبود، پیام قابل فهم و گزینه دانلود بدهید.

افزودن به پیام موجود: `POST /v1/ticket-attachment/create`، multipart شامل
`TicketMessageId` و `File`. فایل با کلید `File` ارسال می‌شود، نه `Attachments`.
تعداد موجود و فایل‌های جدید در مجموع باید حداکثر پنج باشد.

جایگزینی فایل: `POST` یا `PATCH /v1/ticket-attachment/update`، multipart شامل
`Id` و `File`. شناسه فایل و ارتباط آن با پیام حفظ می‌شود. تغییر صرفاً نام فایل
با JSON پشتیبانی نمی‌شود. API حذف فایل نداریم.

متادیتا: `GET /v1/ticket-attachment/read/{id}`؛ لیست متادیتای پیام:
`GET /v1/ticket-attachment/list/{messageId}`. این پاسخ‌ها `fileContent` ندارند.

نمایش: `GET /v1/ticket-attachment/content/{id}`. دانلود: همان مسیر با `?download=true`.
پاسخ باینری با MIME واقعی است؛ این مسیر را از unwrap عمومی JSON عبور ندهید.

### نمایش محافظت‌شده با JWT در React

تگ `<img src="API_URL">` یا `<video src="API_URL">` به‌تنهایی هدر Bearer نمی‌فرستد.
روش قابل اجرا با API فعلی، دریافت Blob هنگام بازکردن پیوست است:

```ts
async function loadAttachment(id: Id, token: string, signal?: AbortSignal) {
  const response = await fetch(`${apiBase}/v1/ticket-attachment/content/${id}`, {
    headers: { Authorization: `Bearer ${token}` },
    signal
  });
  if (!response.ok) throw new Error("دریافت فایل انجام نشد");
  return URL.createObjectURL(await response.blob());
}
```

URL ساخته‌شده را به `<img>` یا `<video controls preload="metadata">` بدهید.
با بسته‌شدن پیش‌نمایش، تغییر فایل، خروج کاربر یا unmount، درخواست را لغو و URL را
با `URL.revokeObjectURL` آزاد کنید. به‌خصوص پس از unmount، URL تازه‌دریافت‌شده را هم
رها کنید تا نشت حافظه ایجاد نشود. ویدئوها را خودکار و هم‌زمان دانلود نکنید.
از نام فایل موجود در متادیتا برای دانلود با لینک `download` استفاده کنید.

این روش ابتدا فایل کامل را دریافت می‌کند. سرور از Range و پاسخ ۲۰۶ پشتیبانی دارد،
اما جریان مستقیم ویدئو با Bearer از طریق `src` به لایه احراز هویت رسانه جدا نیاز دارد؛
وجود این لایه را فرض نکنید. توکن را در URL قرار ندهید و روش کوکی را بدون پشتیبانی
واقعی بک‌اند و CORS به کار نبرید. هدرهای CORS فعلی `Content-Disposition` را expose
می‌کنند؛ برای خواندن هدرهای دیگر با JavaScript ممکن است هماهنگی بک‌اند لازم شود.

## ۱۳. امتیازدهی

امتیاز به **پیام پاسخ** متصل است؛ `ticketId` به مسیر ایجاد امتیاز ارسال نمی‌شود.
کنترل ستاره‌ها را فقط برای مالک تیکت و پیام غیرمالک نمایش دهید.

ایجاد: `POST /v1/ticket-rating/create` با JSON:

```json
{ "ticketMessageId": 26, "score": 5, "comment": "پاسخ مفید بود" }
```

ویرایش: `POST` یا `PATCH /v1/ticket-rating/update`:

```json
{ "id": 8, "score": 4, "comment": null }
```

`score` عدد صحیح ۱ تا ۵ است. `comment` اختیاری و حداکثر ۱۰۲۳ کاراکتر است.
برای پاسخ بدون امتیاز، `read-by-message` مقدار `data: null` می‌دهد؛ به‌جای ثبت
دوباره امتیاز موجود، از شناسه امتیاز و مسیر update استفاده کنید.
مسیر `GET /v1/ticket-rating/read/{id}` هم جزئیات یک امتیاز را می‌دهد.
بعد از تغییر امتیاز، داده همان پیام و گزارش مرتبط را refresh کنید.

## ۱۴. تغییر عنوان، مسئول و وضعیت

`POST` یا `PATCH /v1/ticket/update` با JSON زیر:

```json
{
  "id": 12,
  "subject": "افت فشار آب",
  "assignedToUserId": "11111111-1111-1111-1111-111111111111",
  "statusId": 2
}
```

این عملیات **ویرایش جزئی فیلدها نیست**؛ حتی هنگام PATCH، همه مقادیر بالا را از
آخرین مشخصات تیکت بفرستید. حذف `assignedToUserId` آن را null می‌کند و ممکن است
ارجاع را پاک کند یا برای غیرمدیر خطا بدهد. `null` صریح برای لغو ارجاع فقط برای مدیر است.
مدیر مسئول را از lookup کاربران موجود پروژه انتخاب کند؛ endpoint جدید lookup
ویژه تیکتینگ نداریم. مسئول انتخابی باید کاربر معتبر و فعال سیستم باشد.
کاربر عادی دکمه بستن ندارد. برای نمایش دکمه‌ها از جدول دسترسی بخش ۳ پیروی کنید.
پاسخ update برابر `data: true` است؛ برای مشخصات تازه دوباره read کنید.

## ۱۵. گزارش و تاریخ

`POST /v1/ticket/report` با همان فیلترهای `TicketSearch`؛ صفحه‌بندی در نتیجه گزارش
اثر ندارد، اما اگر فیلدهای صفحه را می‌فرستید باید معتبر باشند.

نمونه `data`:

```json
{
  "ticketCount": 10,
  "ratingCount": 4,
  "averageScore": 4.25,
  "statusCounts": [
    { "statusId": 1, "count": 6 },
    { "statusId": 3, "count": 4 }
  ]
}
```

میانگین از **امتیاز پاسخ‌ها** است؛ ممکن است یک تیکت چند امتیاز داشته باشد.
بدون امتیاز مقدار null را «بدون امتیاز» نمایش دهید، نه صفر.
وضعیتی که در `statusCounts` نیست، برای نمودار صفر در نظر بگیرید و عنوان را از
فهرست وضعیت‌ها بگیرید. دسترسی گزارش دقیقاً مانند فهرست تیکت‌ها محدود می‌شود.

بازه گزارش بر اساس **زمان ایجاد تیکت** است؛ نه زمان پاسخ، امتیاز یا آخرین فعالیت.
امتیازهای همان تیکت‌ها حتی اگر بعد از پایان بازه ثبت شده باشند در میانگین می‌آیند.
`fromDate` شامل ابتدای بازه و `toDateExclusive` خارج از بازه است.
اگر کاربر تاریخ پایان را شامل آن روز انتخاب می‌کند، ابتدای روز بعد در منطقه زمانی
رابط را به UTC تبدیل کنید؛ مقدار `23:59:59` نفرستید و روز را همیشه ۲۴ ساعت فرض نکنید.

زمان‌ها در بک‌اند UTC هستند. به‌دلیل استفاده از `datetime2`، رشته خروجی ممکن است
پسوند `Z` نداشته باشد؛ چنین خروجی‌ای را در adapter این فیچر UTC تفسیر کنید.
برای نمایش به تقویم/منطقه زمانی پروژه تبدیل کنید، اما فیلتر را ISO UTC بفرستید.

## ۱۶. اتصال به API client موجود

نام `ticketingRequest` در مثال‌ها یک adapter است، نه فایل موجود پروژه React.
آن را با client فعلی پروژه پیاده کنید. نمونه زیر فقط قرارداد unwrap را نشان می‌دهد:

```ts
async function ticketingRequest<T>(
  path: string,
  method = "GET",
  body?: unknown,
  signal?: AbortSignal
): Promise<T> {
  const headers = new Headers({ Authorization: `Bearer ${getAccessToken()}` });
  const multipart = body instanceof FormData;
  if (body !== undefined && !multipart) headers.set("Content-Type", "application/json");
  const response = await fetch(`${apiBase}${path}`, {
    method, headers, signal,
    body: body === undefined ? undefined : multipart ? body : JSON.stringify(body)
  });
  const text = await response.text();
  let payload: any;
  try { payload = text ? JSON.parse(text) : undefined; } catch { /* پاسخ غیر JSON */ }
  if (!response.ok || payload?.success !== true) {
    if (response.status === 401) {
      // جریان نشست پروژه را فعال کنید؛ نوشتن‌ها را بی‌قید خودکار تکرار نکنید.
    }
    let messages: string[] = [];
    if (response.status < 500) {
      const errors = payload?.errors;
      messages = Array.isArray(errors)
        ? errors.map((e: { message: string }) => e.message)
        : errors && typeof errors === "object"
          ? Object.values(errors).flat().map(String) : [];
    }
    throw new Error(messages.join("، ") || "انجام درخواست ممکن نشد");
  }
  return payload.data as T;
}
```

`apiBase` و `getAccessToken` باید از تنظیمات و سیستم ورود موجود بیایند؛ مقدار ثابت
یا توکن واقعی داخل کد نگذارید. در client واقعی، کد HTTP و خطاهای فیلدی را هم حفظ کنید
تا رابط بتواند برای ۴۰۱، ۴۱۳ و خطای فرم رفتار جدا داشته باشد.
برای نمایش درصد آپلود، اگر client فعلی آن را پشتیبانی می‌کند استفاده کنید؛ `fetch`
ساده بالا درصد پیشرفت آپلود ارائه نمی‌کند. فایل باینری client جدا از unwrap JSON دارد.

## ۱۷. تازه‌سازی داده و حالت‌های رابط

اگر پروژه cache داده دارد، کلیدها شامل userId، حالت صف، فیلتر و شماره صفحه باشند؛
با خروج یا تغییر کاربر cache و URLهای Blob پاک شوند.

| عملیات موفق | داده‌هایی که باید تازه شوند |
|---|---|
| ثبت تیکت | فهرست مرتبط و گزارش |
| ارسال پیام | جزئیات تیکت، آخرین صفحه پیام‌ها، فهرست و گزارش |
| ویرایش پیام | همان پیام/صفحه، مشخصات تیکت |
| افزودن یا جایگزینی پیوست | متادیتای پیوست‌های پیام، Blob قبلی، مشخصات تیکت |
| ثبت یا ویرایش امتیاز | امتیاز همان پاسخ و گزارش |
| تغییر وضعیت/مسئول/عنوان | جزئیات، فهرست‌های مرتبط و گزارش |

برای هر صفحه حالت بارگیری، خالی، خطا و تلاش مجدد داشته باشید. تیکت با پیام بدون متن
ولی دارای فایل باید درست نمایش داده شود. هنگام ثبت، ارسال دوباره را غیرفعال کنید.
درخواست لغوشده را خطای نمایشی حساب نکنید. داده نهایی سرور بر optimistic state اولویت دارد.
برای مرحله اول به refresh پس از عملیات و refresh دستی اکتفا کنید؛ قرارداد push جدیدی فرض نکنید.

## ۱۸. ترتیب اجرا و معیار تحویل

به‌ترتیب: adapter و typeها ← وضعیت و فهرست ← ثبت تیکت ← گفتگو و پاسخ متنی ←
پیوست و نمایش فایل ← امتیاز ← ارجاع/وضعیت ← گزارش.

پیش از تحویل این سناریوها را با API واقعی یا mock دقیق همین قرارداد بررسی کنید:

- [ ] تیکت متنی، فقط فایل و متن همراه چند فایل ثبت می‌شوند؛ پیام اولیه تکرار نمی‌شود.
- [ ] فرم کاملاً خالی، فایل صفر بایتی، بیش از پنج فایل و فایل بزرگ/نامعتبر رد می‌شوند.
- [ ] شماره پیگیری رشته‌ای از شناسه عددی تفکیک شده و مسیر جزئیات درست باز می‌شود.
- [ ] گفتگو چندصفحه‌ای، پیام‌های هم‌زمان و پیام بدون متن درست نمایش داده می‌شوند.
- [ ] صف «من» و «ارجاع‌شده به من» داده دیگری را نشان نمی‌دهند.
- [ ] تصویر و فیلم با Bearer دریافت می‌شوند؛ URLهای Blob آزاد می‌شوند.
- [ ] دانلود، شکست پخش و فایل غیرقابل دسترس حالت مناسب دارند.
- [ ] بستن تیکت فرم پاسخ را غیرفعال و بازگشایی دوباره آن را فعال می‌کند.
- [ ] فقط مالک به پاسخ دیگری امتیاز می‌دهد و امتیاز قبلی را ویرایش می‌کند.
- [ ] تغییر وضعیت، مسئول قبلی را ناخواسته null نمی‌کند.
- [ ] گزارش میانگین null و وضعیت با تعداد صفر را درست نمایش می‌دهد.
- [ ] خطای ۴۰۰، نشست منقضی، خطای شبکه و پاسخ غیر JSON فرم را از بین نمی‌برند.
- [ ] RTL، صفحه موبایل، کیبورد و وضعیت ارسال در رابط موجود هماهنگ‌اند.

در بک‌اند بررسی‌های Persistence، Application و HTTP با موفقیت اجرا شده‌اند؛
تعداد بررسی‌های نسخه جاری در خروجی `tests/Aban360.Ticketing.SmokeTests` درج می‌شود.
این بررسی‌ها از دیتابیس حافظه‌ای استفاده می‌کنند. ایجاد جداول روی سرور طبق اعلام
مالک پروژه موفق بوده است؛ اما تست کامل API، خواندن/نوشتن فایل و محدودیت آپلود
میزبان باید روی محیط منتشرشده انجام شود. نتیجه تست‌های حافظه‌ای را به معنی تأیید
همه codecهای مرورگر یا عملکرد کامل محیط استقرار تلقی نکنید.

ریسک‌های باز سمت بک‌اند در درخواست‌های هم‌زمان: سقف پیوست در چند درخواست مستقل
هنوز کنترل اتمیک دیتابیس ندارد؛ تغییر وضعیت/مسئول ممکن است با ارسال پیام تداخل کند؛
در ثبت هم‌زمان امتیاز تکراری، قید یکتا داده را حفظ می‌کند ولی درخواست بازنده ممکن است
۵۰۰ دریافت کند. فرانت عملیات تکراری را غیرفعال و داده را پس از خطا تازه کند، اما
حل قطعی این موارد مسئولیت بک‌اند است. شرح کامل در [گزارش بازبینی](REVIEW.fa.md) آمده است.
