# نصب دستی جداول تیکتینگ روی سرور

فایل `InstallTicketing.sql` از SQL مسیر `Up` مایگریشن `1405080401` استخراج شده است.
اجرای آن، بدون اجرای FluentMigrator، ساختار مورد نیاز تیکتینگ را ایجاد می‌کند.
فقط پنج جدول جدید در اسکیمای `UserPool` و چهار وضعیت اولیه تیکت ساخته می‌شوند.
جدول کاربران قبلی تغییر نمی‌کند و کلیدهای خارجی به همان جدول متصل می‌شوند.

## مراحل اجرا

1. از دیتابیس مقصد بکاپ قابل بازیابی بگیرید؛ ابتدا اسکریپت را روی نسخه تست بازیابی‌شده اجرا کنید.
2. در SSMS به **SQL Server ویندوزی سرور** وصل شوید و دیتابیس مورد استفاده برنامه را انتخاب کنید.
3. فایل `InstallTicketing.sql` را باز کنید و مقدار `REPLACE_WITH_DATABASE_NAME` را با نام دقیق دیتابیس عوض کنید.
4. FILESTREAM باید فعال و Filegroup پیش‌فرض آن دارای Container فعال و قابل‌نوشتن باشد.
   راهنمای آماده‌سازی دستی در کامنت ابتدای فایل
   `Aban360.UserPool.Persistence/Migrations/1405_08_04_Ticketing.cs` موجود است.
   این اسکریپت نصب، تنظیمات سرور یا Filegroup را خودش تغییر نمی‌دهد.
5. **تمام فایل** را یکجا، خارج از تراکنش دیگری اجرا کنید؛ فقط قسمت CREATE را انتخاب و اجرا نکنید.
6. پیام `Ticketing installation committed successfully.` و خروجی‌های بررسی را کنترل کنید:
   پنج جدول، هشت کلید خارجی فعال و معتبر، FILESTREAM روی FileContent، ROWGUIDCOL روی FileGuid و چهار وضعیت.

قبل از شروع، نام دیتابیس، وجود UserPool.User، نوع Guid شناسه کاربر و پیش‌نیازهای
FILESTREAM بررسی می‌شوند. اگر یکی از جداول هدف از قبل موجود باشد، اسکریپت متوقف
می‌شود و آن را بازسازی، حذف یا جایگزین نمی‌کند. اگر داخل بخش نصب خطایی رخ دهد،
تراکنش همان نصب rollback می‌شود؛ اسکریپت با وجود خطا پیام موفقیت چاپ نمی‌کند.
بخش بررسی خروجی‌ها فقط خواندنی است و بعد از commit اجرا می‌شود.

اگر خطای `51107` گرفتید، حالت `IMPLICIT_TRANSACTIONS` نشست روشن است. در یک
Query جدا و خارج از تراکنش باز، `SET IMPLICIT_TRANSACTIONS OFF;` را اجرا کنید
و سپس کل فایل نصب را دوباره اجرا کنید. اسکریپت تراکنش باز قبلی شما را commit یا
rollback نمی‌کند و در این وضعیت نصب را شروع نمی‌کند.

ساختار کلید یکتای `UserPool.User.Id` و قابل‌نوشتن بودن دیتابیس هم قبل از شروع
بررسی می‌شود. دستورات ساخت در یک batch داخلی اجرا می‌شوند تا خطاهای compilation
آن بخش هم به CATCH بیرونی برسند. پیش از COMMIT، تعداد جدول‌ها و روابط، FILESTREAM،
ROWGUIDCOL و وضعیت‌های اولیه کنترل می‌شوند. تنظیم قبلی XACT_ABORT نشست نیز بازگردانده می‌شود.

## پس از نصب

نسخه جدید برنامه باید منتشر شده و به همین دیتابیس وصل باشد. ابتدا ورود و دریافت
وضعیت‌ها را بررسی کنید، سپس یک تیکت آزمایشی، پاسخ، فایل کوچک، امتیاز و گزارش را
از طریق API تست کنید. موفقیت CREATE TABLE به‌تنهایی تأیید عملکرد تمام APIها، مجوزها،
تنظیمات آپلود میزبان یا پخش فیلم در مرورگر نیست.

اجرای خودکار مایگریشن در `ConfigureMigrationsAndSeeds.cs` فعلاً غیرفعال است و
برای استفاده از این جداول لازم نیست فعال شود. فایل SQL، تاریخچه `VersionInfo`
را دست‌کاری نمی‌کند. **اگر در آینده FluentMigrator دوباره فعال شود، باید نسخه
1405080401 پس از تطبیق کامل ساختار با روش کنترل‌شده در تاریخچه آن همگام شود**؛
در غیر این صورت تلاش می‌کند همین جداول موجود را دوباره ایجاد کند. صرفاً برای دورزدن
خطا، رکورد تاریخچه را دستی و بدون بررسی ساختار درج نکنید.

این فایل در محیط تهیه، از نظر تطابق با SQL مایگریشن و نبود دستورات حذف/تغییر
جداول قبلی بررسی شده است؛ اجرای واقعی آن روی دیتابیس سرور هنوز انجام نشده است.

برای تکرار بررسی تطبیق ساختار بدون اتصال به دیتابیس، از ریشه مخزن اجرا کنید:

```powershell
./docs/ticketing/sql/Test-InstallTicketing.ps1
```

این بررسی، SQL ساخت جداول را پس از بازکردن رشته SQL با مایگریشن مقایسه می‌کند؛
جای parser یا اجرای SQL Server را نمی‌گیرد. در بازبینی اخیر سرویس Docker در دسترس
نبود و تست اجرایی انجام نشد.

مبنای کنترل تراکنش و خطا:
[IMPLICIT_TRANSACTIONS](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-implicit-transactions-transact-sql)،
[TRY/CATCH و خطاهای سطح پایین‌تر](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/try-catch-transact-sql).
