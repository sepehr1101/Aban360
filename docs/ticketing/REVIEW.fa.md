# نتیجه بازبینی تیکتینگ

این بازبینی شامل Entity، مایگریشن، تنظیمات EF، سرویس‌های Persistence، Handlerها،
APIها، قرارداد فرانت و تست‌هاست. بررسی کد و تست حافظه‌ای جای اجرای واقعی SQL Server
ویندوزی و FILESTREAM را نمی‌گیرد.

## موارد اصلاح‌شده

### محدودیت پیوست در یک Unit of Work

قبلاً کنترل تعداد فایل فقط رکوردهای ذخیره‌شده را می‌شمرد. اگر در یک عملیات چند
پیوست اضافه می‌شد و SaveChanges در پایان انجام می‌گرفت، تعداد فایل‌های pending
دیده نمی‌شد و امکان عبور از سقف پنج فایل وجود داشت.

اکنون `ITicketAttachmentQueryService.CountByMessage` تعداد ذخیره‌شده و پیوست‌های
Added در همان Context را محاسبه می‌کند و Handler پیش از افزودن فایل از آن استفاده
می‌کند. محتوای فایل برای شمارش خوانده نمی‌شود. تست اختصاصی اضافه شد: پیام دارای دو
پیوست، سه پیوست دیگر را پیش از commit قبول می‌کند و فایل ششم را رد می‌کند.

### پیش‌نیاز FILESTREAM

مایگریشن فقط وجود Filegroup پیش‌فرض را بررسی می‌کرد. بررسی اکنون شامل نوع FD،
پیش‌فرض بودن، قابل‌نوشتن بودن و وجود container با وضعیت ONLINE است. راهنمای دستی
موجود در همان فایل حفظ شده است. مایگریشن روی دیتابیس واقعی اجرا نشده است.

### هماهنگی سبک کد

namespaceهای فیچر به شکل بلوکی رایج در فیچرهای قبلی تبدیل شدند؛ سازنده‌های
Application پارامترها را مانند نمونه‌های قبلی در خطوط جدا می‌گیرند. بررسی null
در کد فیچر با `NotNull` موجود پروژه هماهنگ شد. ساختار Commands/Queries، پوشه‌های
Contracts/Implementations، متد Handle، AutoMapper، FluentValidation و commit در
کنترلر حفظ شده‌اند. مسیرهای عمومی API و شکل DTOها تغییر نکرده‌اند.

## ارتباط کاربران و جریان اصلی

- `Ticket.CreatedByUserId` و `Ticket.AssignedToUserId` به `[UserPool].[User].[Id]` وصل‌اند.
- `TicketMessage.SenderUserId` پاسخ‌دهنده واقعی هر پیام را حفظ می‌کند؛ ارجاع مجدد
  تیکت آن را تغییر نمی‌دهد.
- `TicketRating.RatedByUserId` ثبت‌کننده امتیاز را مشخص می‌کند.
- هویت ایجادکننده/فرستنده/امتیازدهنده از نشست جاری می‌آید.
- مسیر `my-list` حتی برای مدیر، مالک را به کاربر جاری محدود می‌کند.
- خروجی لیست‌ها بدون محتوای فایل است؛ خواندن محتوای فایل پس از بررسی دسترسی انجام می‌شود.

## موارد باز و ریسک‌های هم‌زمانی

این موارد هنوز اصلاح نشده‌اند و برای بار هم‌زمان باید در نظر گرفته شوند:

| مورد | رفتار ممکن | اقدام لازم |
|---|---|---|
| سقف پیوست بین دو درخواست مستقل | هر دو درخواست، تعداد قدیمی را می‌خوانند و مجموع ممکن است از پنج بیشتر شود؛ اصلاح pending فقط داخل یک Context است | کنترل اتمیک در دیتابیس یا تراکنش/قفل‌گذاری مناسب همراه تست هم‌زمانی |
| تغییر وضعیت یا مسئول هم‌زمان با ارسال پیام | شرط دسترسی/بسته‌بودن پیش از commit خوانده می‌شود؛ عملیات دیگر می‌تواند وضعیت یا مسئول را تغییر دهد و نوشتن بعدی تغییر را بپوشاند | سیاست concurrency برای تیکت و پاسخ قابل فهم conflict، همراه تست دو نشست |
| امتیاز تکراری در دو درخواست هم‌زمان | قید UNIQUE جلوی دو امتیاز را می‌گیرد، اما خطای ذخیره درخواست بازنده در exception handler فعلی ممکن است ۵۰۰ شود | تبدیل خطای unique مربوط به این عملیات به conflict/خطای دامنه، همراه تست روی SQL Server |

این موارد با تست‌های فعلی که تک‌عملیاتی و حافظه‌ای‌اند تأیید یا رد نمی‌شوند.
نباید نتیجه تست‌ها به معنی تأیید رفتار هم‌زمان SQL Server معرفی شود.

## محدودیت‌های شناخته‌شده قرارداد

- دریافت فایل فعلاً byte array است؛ HTTP Range وجود دارد، اما streaming مستقیم
  دیتابیس پیاده نشده است. آپلود و نمایش چند فایل بزرگ مصرف حافظه قابل توجه دارد.
- تاریخچه ارجاع‌ها و audit ویرایش پیام نداریم؛ فقط مسئول فعلی، نویسنده اصلی و زمان ایجاد حفظ می‌شوند.
- DTOها نام کاربران را ندارند و فرانت به lookup کاربران برای نام کامل نیاز دارد.
- تاریخ‌های `datetime2` ممکن است بدون پسوند UTC برگردند؛ adapter فرانت طبق راهنما آن‌ها را UTC تفسیر می‌کند.
- محدودیت واقعی آپلود روی IIS/reverse proxy و قابلیت پخش codec مرورگر باید در محیط استقرار تست شود.

## اعتبارسنجی

پس از اصلاحات، ۳۷ بررسی Persistence، ۶۵ بررسی Application و ۸۹ بررسی HTTP
موفق بودند؛ مجموع ۱۹۱ بررسی. تست‌های SQL Server واقعی، اجرای Up/Down مایگریشن،
FILESTREAM و هم‌زمانی چند نشست انجام نشده‌اند. خروجی بیلد دارای هشدارهای قبلی
پروژه است؛ موفقیت بیلد به معنی نبود هشدار در کل مخزن نیست.
