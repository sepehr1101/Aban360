# مشخصات صفحه گزارش قرائت خودکار

## هدف

یک صفحه فارسی و راست‌به‌چپ برای بررسی مصرف و وضعیت کنتور طراحی شود. مصرف بین قرائت‌ها محور اصلی صفحه باشد و نمودارهای دبی، دما و سلامت دستگاه آن را تکمیل کنند. طراحی با سیستم بصری فعلی محصول هماهنگ باشد؛ این سند انتخاب کتابخانه نمودار را به فرانت واگذار می‌کند.

## قرارداد API

`POST /v1/auto-reading/flow-meter-report`

هدر `Content-Type: application/json` و احراز هویت معمول برنامه الزامی است. ورودی فقط سه فیلد زیر در بدنه JSON دارد؛ Query String استفاده نشود:

| نام | نوع | نمونه |
| --- | --- | --- |
| fromDate | رشته، تاریخ شمسی معتبر با ارقام انگلیسی و قالب yyyy/MM/dd | 1405/06/01 |
| toDate | رشته، تاریخ شمسی معتبر با ارقام انگلیسی و قالب yyyy/MM/dd | 1405/06/30 |
| billId | رشته شناسه قبض مشترکِ کاردکس جاری | "4441707016311" |

```json
{
  "fromDate": "1405/06/01",
  "toDate": "1405/06/30",
  "billId": "4441707016311"
}
```

`billId` باید از اطلاعات مشترک انتخاب‌شده در کاردکس خوانده شود؛ به عدد تبدیل نشود و در فرانت روی شناسه نمونه ثابت نشود. تاریخ پایان نباید قبل از تاریخ شروع باشد. تقویم می‌تواند ارقام فارسی نمایش دهد اما تاریخ ارسالی ارقام انگلیسی داشته باشد.

در نسخه فعلی بک‌اند فقط تطابق دقیق شناسه قبض `4441707016311` را می‌پذیرد. برای هر رشته دیگری، بدون فراخوانی سرویس خارجی، پاسخ ۴۰۰ با پیام دقیق `نوع کنتور اولتراسونیک نیست` برمی‌گرداند. فرانت نباید این شرط را جایگزین فراخوانی API کند؛ تصمیم معتبر بودن نوع کنتور با بک‌اند است. ورودی عددی، بدنه نامعتبر یا نبود فیلد اجباری نیز ممکن است در مرحله مدل‌بندی ASP.NET Core با پاسخ اعتبارسنجی ۴۰۰ رد شود.

پارامترهای `FlowMeterSerial = PYC-929801010342` و `FlowMeterType = 3` در Handler داخلی ثابت هستند. فرانت این دو فیلد را نه در فرم دریافت کند و نه در درخواست بفرستد. فراخوانی سرویس خارجی همچنان GET است؛ این موضوع داخلی بک‌اند است و endpoint مورد استفاده فرانت فقط POST است.

احراز هویت درخواست مطابق سایر APIهای برنامه است. توکن ESB در بک‌اند مدیریت می‌شود و فرانت فقط API داخلی را فراخوانی می‌کند.

پاسخ موفق داخل `ApiResponseEnvelope` و در فیلد `data` قرار می‌گیرد. نام فیلدهای مدل در JSON خروجی مطابق پیش‌فرض ASP.NET Core به‌صورت camelCase است:

```json
{
  "success": true,
  "httpStatusCode": 200,
  "data": {
    "readAllReportModelList": [],
    "ultraSonicReadAllReportModelList": []
  }
}
```

این نمونه فقط بخش‌های مورد نیاز را نشان می‌دهد؛ فیلدهای عمومی پیام و خطای Envelope نیز وجود دارند. فهرست اول فعلاً ساختار مستندشده‌ای ندارد و محتوای آن بدون مدل‌سازی منتقل می‌شود. نمودارهای این نسخه از `ultraSonicReadAllReportModelList` ساخته شوند. اگر فقط فهرست اول داده داشت، پیام «نمایش این نوع گزارش هنوز پشتیبانی نمی‌شود» نمایش داده شود، نه «قرائتی ثبت نشده است».

`environmentTemperature` در خروجی بک‌اند عدد nullable است، اگرچه در نمونه سرویس اصلی رشته بود. سایر مقادیر سنجشی هم nullable هستند. `pressure`، `wirelessSimCard` و `valveOperationFlag` به دلیل خالی بودن در نمونه و نامشخص بودن نوع واقعی، فعلاً JSON خام nullable هستند؛ پیش از استفاده عددی، نوع مقدار بررسی شود. بک‌اند مقادیر اصلی را برمی‌گرداند و مصرف مشتق‌شده یا سری مخصوص نمودار تولید نمی‌کند.

خطای اعتبارسنجی ۴۰۰، خطای ارتباط یا پاسخ نامعتبر سرویس بالادست ۵۰۲ و پایان مهلت سرویس ۵۰۴ است. خطاهای احراز هویت برنامه مطابق رفتار عمومی محصول مدیریت شوند. خطای سرویس نباید به نمودار خالی یا مصرف صفر تبدیل شود.

نمونه بخش‌های ثابت پاسخ برای شناسه قبض پشتیبانی‌نشده:

```json
{
  "success": false,
  "httpStatusCode": 400,
  "successMessage": null,
  "data": null,
  "errors": [{ "code": 0, "message": "نوع کنتور اولتراسونیک نیست" }],
  "warnings": null
}
```

فیلد `meta` نیز توسط Envelope اضافه می‌شود. متن خطا از `errors[].message` خوانده شود؛ `errors[].code` در خطای نوع کنتور صفر است و کد HTTP نیست. برای خطاهای مدل‌بندی بدنه، قالب عمومی `ValidationProblemDetails` و فیلد `errors` از نوع object نیز پشتیبانی شود. کلاینت بر اساس HTTP status و `success` تصمیم بگیرد، نه وجود آرایه خالی. در پاسخ ۴۰۰ نوع کنتور، نمودار و خلاصه قبلی پاک و همان متن خطا داخل پنل نشان داده شود؛ تلاش مجدد خودکار انجام نشود. ۵۰۲/۵۰۴ پیام فارسی و دکمه تلاش مجدد داشته باشند. GET قدیمی دیگر قرارداد این endpoint نیست.

## چیدمان و تعامل

۰. بالای کاردکس آب‌بها و در نوار دکمه‌های همان کاردکس، دکمه‌ای با عنوان «گزارش قرائت خودکار» و آیکن نمودار قرار گیرد. با کلیک، یک پنل تمام‌عرض در همان صفحه، بالای جدول کاردکس و زیر نوار دکمه‌ها باز شود. این پنل به‌طور پیش‌فرض مخفی است. کلیک مجدد آن را می‌بندد. نمایش گزارش در صفحه یا مسیر جداگانه لازم نیست. شناسه قبض از مشترک جاری گرفته و در عنوان پنل فقط خواندنی نمایش داده شود. در نبود مشترک جاری، دکمه غیرفعال باشد.

۱. نوار فیلتر داخل پنل فقط شامل تاریخ شروع، تاریخ پایان و دکمه «نمایش گزارش» باشد. در باز شدن اولیه، تاریخ‌های کاردکس جاری استفاده شوند؛ اگر کاردکس بازه‌ای ندارد، دو تاریخ خالی بمانند و کاربر انتخاب کند. درخواست فقط پس از تکمیل تاریخ معتبر و زدن «نمایش گزارش» ارسال شود. سریال و نوع کنتور فیلتر نیستند.

۲. کارت‌های خلاصه: مصرف مستقیم در بازه قرائت‌های موجود، مصرف معکوس در همان بازه، آخرین دبی ثبت‌شده و زمان آخرین قرائت. زمان ابتدا و انتهای پوشش واقعی داده زیر کارت‌های مصرف مشخص باشد. با کمتر از دو قرائت معتبر، مصرف «قابل محاسبه نیست» نمایش داده شود.

۳. نمودار اصلی تمام‌عرض با دو تب: «مصرف بین قرائت‌ها» به‌عنوان پیش‌فرض و «شمارنده تجمعی».

۴. ردیف دوم شامل نمودار مستقل «دبی در زمان قرائت» و نمودار مشترک «دمای آب و محیط». در موبایل زیر هم قرار گیرند.

۵. داخل پنل گزارش و بعد از نمودارهای اصلی، یک Accordion با عنوان «سلامت کنتور و اطلاعات فنی» قرار گیرد. `defaultExpanded = false` باشد: در شروع فقط سربرگ و فلش باز/بسته شدن دیده شود و تمام محتوای سلامت مخفی باشد. رفتار دقیق آن در بخش بعد آمده است.

۶. جدول جزئیات قرائت‌ها زیر نمودارها و آکاردئون قرار گیرد؛ ستون‌های پیش‌فرض زمان قرائت، شمارنده‌ها، دبی و دما باشند. باتری، سیگنال و مشخصات فنی داخل آکاردئون سلامت بمانند تا اطلاعات سلامت در حالت بسته در بخش اصلی تکرار نشوند.

### رفتار دقیق آکاردئون سلامت

- این آکاردئون داخل پنل قرائت خودکار است؛ دکمه بالای کاردکس پنل کامل را باز می‌کند و سربرگ آکاردئون فقط جزئیات سلامت را باز می‌کند. این دو کنترل مستقل هستند.
- محتوای مخفی شامل نمودار ولتاژ دو باتری، نمودار سیگنال، نمودار بازشدگی شیر، فشار در صورت وجود داده، وضعیت درپوش، کد وضعیت شیر، مقدار ESR باتری و مشخصات فنی دستگاه مانند IMEI و نسخه‌ها است.
- داخل آکاردئون، باتری و سیگنال در یک ردیف دو ستونی و شیر و فشار در ردیف بعد قرار گیرند؛ در موبایل همه تک‌ستونی شوند. وضعیت‌های غیرعددی به‌صورت متن یا Badge خنثی و دارای زمان مشاهده نمایش داده شوند، نه نمودار دایره‌ای یا سطح هشدار حدسی.
- سربرگ با کلیک، Enter و Space قابل استفاده باشد؛ `aria-expanded` و `aria-controls` تنظیم شوند. محتوای بسته وارد ترتیب فوکوس نشود.
- هنگام بازشدن آکاردئون، نمودارها ساخته یا resize شوند تا ابعاد صفر نگیرند. باز/بسته کردن آکاردئون درخواست جدید API ایجاد نکند؛ داده همان گزارش استفاده شود.
- با تغییر مشترک یا بسته شدن کل پنل، درخواست در حال اجرا لغو، نمایش قبلی پاک و آکاردئون سلامت به حالت بسته برگردد. با فیلتر مجدد نیز تا دریافت نتیجه جدید داده قدیمی با تاریخ جدید نشان داده نشود.

رنگ اصلی مصرف مستقیم آبی و معکوس نارنجی باشد. رنگ، نوع خط و عنوان سری‌ها در تمام صفحه ثابت بمانند. نقاط قرائت واقعی مشخص، شبکه نمودار کم‌رنگ و متن‌ها خوانا باشند. از منحنی‌های بسیار نرم و نمودار سه‌بعدی استفاده نشود. راهنمای شناور با لمس و ماوس قابل دسترسی باشد و زمان کامل، مقدار و واحد تأییدشده را نشان دهد. علاوه بر رنگ، از راهنما و نوع خط برای تمایز سری‌ها استفاده شود.

بازه زمانی و زوم نمودارها هماهنگ باشد. نشانگر زمان مشترک فقط مقدار قرائت همان زمان را نشان دهد؛ در نبود قرائت، مقدار ساختگی یا مقدار نزدیک بدون اعلام زمان واقعی نمایش داده نشود. امکان مخفی‌کردن هر سری از راهنما وجود داشته باشد. صفحه RTL باشد، اما زمان روی محور افقی از قدیم به جدید و از چپ به راست پیش برود.

## مشخصات نمودارها

| عنوان | فیلدها | نوع و مختصات |
| --- | --- | --- |
| مصرف بین قرائت‌ها | تفاضل positiveTotalConsumption و تفاضل negativeTotalConsumption | Grouped Vertical BarChart / ColumnChart؛ دو ستون کنار هم برای هر فاصله؛ یک محور عمودی مشترک؛ stacked=false |
| شمارنده تجمعی | positiveTotalConsumption و negativeTotalConsumption | Multi-series LineChart؛ دو خط با marker واقعی در یک مختصات؛ interpolation=linear؛ همان واحد و مقیاس |
| دبی در زمان قرائت | instantFlow | LineChart with Markers؛ خط مستقیم بین نقاط مجاور معتبر؛ مستقل؛ محور شامل صفر و مقادیر منفی؛ رنگ متفاوت برای مقادیر منفی |
| دمای آب و محیط | waterTemperature و environmentTemperature | Multi-series LineChart؛ دو خط linear در یک مختصات، مشروط به یکسان بودن واحد |
| ولتاژ باتری‌ها | batteryVoltage و backupBatteryVoltage | Multi-series LineChart؛ دو خط linear در یک مختصات؛ فقط در آکاردئون سلامت؛ عنوان «ولتاژ»، نه «درصد شارژ» |
| قدرت سیگنال | antennaSignal | LineChart with Markers؛ مستقل در آکاردئون سلامت؛ بدون تبدیل حدسی به درصد یا dBm |
| بازشدگی شیر | valveOpenPercent | StepLineChart / Stepped LineChart؛ محور ۰ تا ۱۰۰؛ در آکاردئون سلامت؛ داده نامعتبر یا شکاف طولانی اتصال نداشته باشد |
| فشار | pressure | LineChart؛ مستقل در آکاردئون سلامت، فقط برای داده عددی معتبر و با واحد تأییدشده |

نام نوع‌ها مفهومی است و باید به معادل کتابخانه فعلی فرانت نگاشت شود. برای این گزارش PieChart، DoughnutChart، GaugeChart، Stacked BarChart و نمودار سه‌بعدی استفاده نشود؛ هدف نمایش روند و مقایسه زمانی است و درصد سلامت یا سهم از کل در قرارداد تعریف نشده است. کارت‌های خلاصه نیز کارت عددی هستند، نه Gauge.

در همه نمودارها x زمان قرائت و y مقدار سری است. در BarChart، x زمان پایان فاصله و Tooltip شامل ابتدا و انتهای آن است. ولتاژ، دما و سایر کمیت‌ها محور y مستقل دارند؛ فقط سری‌های هم‌واحد نام‌برده در یک مختصات مشترک قرار می‌گیرند. `connectNulls=false` و `smoothing=false` باشد؛ خط یا پله بین مشاهده‌ها صرفاً راهنمای دیدن تغییرات است و اندازه‌گیری پیوسته را اثبات نمی‌کند.

دبی، مصرف، دما، ولتاژ و سیگنال روی یک محور عمودی ادغام نشوند. دو محور عمودی متفاوت در نسخه اولیه نیاز نیست. داده ثابت، مثل باتری ۳٫۷، به‌صورت خط ثابت واقعی نمایش داده شود؛ برای ایجاد جذابیت بصری نباید نوسان ساختگی تولید شود.

## آماده‌سازی و محاسبات

- ابتدا داده‌ها بر اساس سریال تفکیک و سپس بر اساس `greDateTimeReadAll` صعودی مرتب شوند؛ ترتیب دریافتی قابل اتکا نیست. محور زمانی واقعی باشد، نه فهرست برچسب‌های با فاصله مساوی.
- زمان اصلی نمودار، زمان قرائت است؛ `greServerDateTime` زمان دریافت سرور است. نمایش تاریخ شمسی و ساعت از `persianDateTimeReadAll` یا تبدیل هماهنگ زمان قرائت استفاده کند.
- زمان‌های سرویس offset ندارند. بدون تأیید منطقه زمانی سرویس، به آنها Z اضافه نشود و زمان‌ها بر اساس منطقه زمانی مرورگر جابه‌جا نشوند.
- برای دو قرائت متوالی معتبر: `positiveDelta = current.positiveTotalConsumption - previous.positiveTotalConsumption` و `negativeDelta = current.negativeTotalConsumption - previous.negativeTotalConsumption`.
- مقدار معکوس یک حجم مستقل است؛ به دلیل نام آن، عدد را منفی نکنید. نمایش «مصرف خالص» از تفاضل دو حجم تا تأیید معنای تجاری فیلدها انجام نشود.
- اولین قرائت فاقد مصرف بازه‌ای است. قرائت با زمان نامعتبر، زمان تکراری متعارض یا شمارنده خالی نباید مبنای تفاضل ساختگی شود. رکورد کاملاً تکراری حذف شود؛ تعارض در زمان یکسان به‌عنوان کیفیت داده مشخص و از محاسبه بازه مربوط کنار گذاشته شود.
- اگر تفاضل شمارنده منفی بود، مصرف آن فاصله نامعتبر است؛ آن را صفر یا قدرمطلق نکنید. پیام «کاهش شمارنده؛ نیازمند بررسی» نمایش داده شود. در بازه دارای کاهش یا داده ناقص، جمع کل کامل اعلام نشود؛ در صورت نمایش جمع فاصله‌های معتبر، عنوان «جمع بخش‌های معتبر» و هشدار پوشش ناقص داشته باشد.
- ستون مصرف به زمان انتهای فاصله متصل باشد و راهنمای آن زمان شروع، زمان پایان و طول فاصله را نشان دهد. دو ستون مقایسه‌ای همیشه به همان فاصله تعلق دارند. ستون‌ها از صفر شروع شوند.
- اختلاف بین روزهای ۱۸ و ۲۲، مصرف فاصله این دو قرائت است؛ عنوان «مصرف روزانه» نگیرد. قابلیت اختیاری «میانگین روزانه در فاصله دو قرائت» از تقسیم حجم بر مدت واقعی فاصله بر حسب روز به دست می‌آید و با همین عنوان مشخص نمایش داده شود.
- مصرف فاصله چندروزه معتبر قابل نمایش است، اما داده روزهای داخل آن قابل استنتاج نیست. شکاف زمانی در نمودارهای سنجش لحظه‌ای با فاصله یا خط‌چین و توضیح نبود قرائت مشخص شود؛ منحنی پیوسته ادعای اندازه‌گیری پیوسته نکند.
- مقدار `null` یا نامعتبر از صفر متمایز است و با «—» نمایش داده شود. صفر یک قرائت واقعی است. مقادیر منفی دبی حفظ شوند.
- مصرف از انتگرال‌گیری دبی این نمونه محاسبه نشود؛ نمونه‌برداری برای بازسازی جریان تمام ساعات کافی نیست.
- دقت محاسبه حفظ و فقط هنگام نمایش گرد شود. تعداد اعشار پس از تأیید واحدها قابل تنظیم باشد.

## وضعیت‌ها و اطلاعات نامشخص

حالت بارگذاری، پاسخ بدون قرائت، تک‌قرائت، داده ناقص، خطای سرویس و تلاش مجدد طراحی شوند. با تغییر فیلتر، درخواست قبلی لغو یا پاسخ قدیمی نادیده گرفته شود. داده قبلی نباید زیر عنوان بازه جدید به‌عنوان نتیجه جدید نمایش داده شود.

واحد حجم، دبی، دما و فشار، مقیاس سیگنال، معنی کدهای `currentValveState`، `operationMode` و `communicationMethod` و معنی مقدار `leakDetectionValvePercent = -1` باید از ارائه‌دهنده تأیید شوند. تا آن زمان واحد حدسی و برچسب‌هایی مثل «شیر بسته»، «باتری ضعیف»، «نشتی» یا «سیگنال خوب» نمایش داده نشوند. کد خام وضعیت با عنوان «کد وضعیت» قابل نمایش است. بازه خارج از ۰ تا ۱۰۰ برای درصد شیر به‌عنوان نامعتبر مشخص شود و به محدوده بریده نشود.

`openDoor` را به‌صورت وضعیت مشاهده‌شده یا نشانگر رویداد همراه با زمان موجود نمایش دهید؛ از آن مدت دقیق بازبودن درپوش نتیجه نگیرید. تأخیر ظاهری دریافت از تفاضل دو زمان به دلیل احتمال اختلاف ساعت دستگاه و سرور، معیار قطعی کیفیت ارتباط نیست.

## معیار پذیرش با نمونه ارسالی

- دکمه «گزارش قرائت خودکار» بالای کاردکس آب‌بها وجود داشته باشد؛ پنل در ابتدا مخفی و پس از کلیک در همان صفحه باز شود.
- درخواست شبکه دقیقاً POST با JSON سه‌فیلدی `fromDate`، `toDate` و `billId` رشته‌ای باشد؛ سریال و نوع کنتور در ورودی UI یا درخواست وجود نداشته باشند.
- شناسه قبض از مشترک جاری خوانده شود؛ شناسه غیرپشتیبانی‌شده پیام دقیق «نوع کنتور اولتراسونیک نیست» را نشان دهد و نتیجه مشترک قبلی باقی نماند.
- آکاردئون سلامت در شروع بسته باشد؛ نمودارهای باتری، سیگنال، شیر، فشار و اطلاعات فنی قبل از باز کردن آن دیده نشوند. بازشدن آن درخواست شبکه دیگری ایجاد نکند و نمودارها اندازه صحیح داشته باشند.
- نمودار مصرف Grouped BarChart، شمارنده‌ها و دما Multi-series LineChart، دبی و سیگنال LineChart with Markers و شیر StepLineChart باشند؛ PieChart استفاده نشود.
- ۱۸ قرائت نمونه به ترتیب زمانی نمایش داده شوند.
- افزایش شمارنده مستقیم بین اولین و آخرین قرائت `18.868` و افزایش شمارنده معکوس `3.681` است؛ کارت‌ها بازه واقعی قرائت‌ها را نشان دهند، نه ادعای پوشش کامل ماه.
- دبی `-0.01` زیر خط صفر و مقدار `0.14` در زمان درست دیده شود.
- دمای محیط عددی و قابل مقایسه با دمای آب باشد؛ باتری اصلی ۳٫۷ و پشتیبان ۳٫۴/۳٫۵ مطابق داده نمایش داده شوند.
- فشار در نمونه فاقد داده است و نباید خط صفر تولید کند.
- شکاف روزهای ۱۸ تا ۲۲ با مصرف یک‌روزه اشتباه نشود؛ با یک قرائت، نمودار مقادیر لحظه‌ای نمایش داده شود ولی مصرف قابل محاسبه نباشد.
- حذف یک مقدار، کاهش شمارنده، پاسخ خالی و خطای سرویس هرکدام حالت درست و متمایز داشته باشند.
