# ثبت درخواست‌های صدور قبض آنی

پیش از انتشار نسخه جدید API، فایل زیر را دستی روی SQL Server میزبان Atlas اجرا کنید:

`Aban360.OldCalcPool.Persistence/Migrations/Manual/Atlas/001_NowGenerateBillRequest.sql`

اسکریپت دیتابیس Atlas را انتخاب می‌کند و جدول `dbo.NowGenerateBillRequest` و ایندکس روز درخواست را می‌سازد. اجرای مجدد، اطلاعات جدول موجود را حذف نمی‌کند. برنامه از اتصال `ReportConnection` برای دسترسی به این جدول استفاده می‌کند؛ کاربر این اتصال باید مجوز SELECT و INSERT روی جدول و امکان گرفتن قفل تراکنشی در Atlas را داشته باشد.

در ابتدای پردازش `POST /v1/generate-bill/now`، تعداد درخواست‌های همان روز بررسی و سپس یک سطر درج می‌شود. این مرحله پیش از اعتبارسنجی ورودی و محاسبه انجام می‌شود؛ بنابراین درخواست‌های ناموفق، ورودی‌های نامعتبر و درخواست‌های ردشده به علت سقف روزانه نیز ثبت و شمارش می‌شوند. درخواست‌هایی که پیش از ورود به handler توسط چارچوب API رد شوند، وارد جدول نمی‌شوند.

- ده درخواست نخست هر موبایل مجاز است؛ درخواست یازدهم و بعدی با کد خطای ۱۰ رد می‌شود.
- سه درخواست نخست هر شناسه قبض، در مجموع از تمام موبایل‌ها، مجاز است؛ درخواست چهارم و بعدی با کد خطای ۱۱ رد می‌شود.
- در صورت رسیدن به هر دو سقف، پیام سقف موبایل اولویت دارد.
- پاسخ هر دو محدودیت، HTTP 429 است و پیام و کد اختصاصی در `Data` پاسخ قرار می‌گیرد.
- روز از نیمه‌شب تا نیمه‌شب، مطابق تاریخ محلی SQL Server (`SYSDATETIME`) محاسبه می‌شود.
- فاصله ابتدا و انتهای موبایل و شناسه قبض برای ثبت و شمارش حذف می‌شود.

ستون `LimitErrorCode` فقط نتیجه کنترل سقف در زمان ورود درخواست است: صفر یعنی عبور از کنترل سقف؛ به معنی صدور موفق قبض نیست. زمان درخواست، روز درخواست، موبایل، شناسه قبض و رقم اعلام‌شده کنتور نیز ثبت می‌شوند.

کنترل تعداد و درج سطر در یک تراکنش، با قفل‌های اختصاصی موبایل و شناسه قبض انجام می‌شود. قفل‌ها در Atlas هستند و میان نمونه‌های متعدد API نیز مشترک‌اند. تراکنش پیش از محاسبه قبض پایان می‌یابد.

## بررسی

آزمون بدون اتصال به دیتابیس:

```powershell
dotnet run --project tests/Aban360.NowGenerateBill.SmokeTests/Aban360.NowGenerateBill.SmokeTests.csproj
```

این آزمون ثبت سرویس، توقف پردازش هنگام رسیدن به سقف، تقدم ثبت درخواست بر اعتبارسنجی، انتقال توکن لغو، پاسخ HTTP 429 کنترلر و صف‌کردن پیامک عدم صدور قبض را بررسی می‌کند. آزمون پیامک واقعی ارسال نمی‌کند.

## پیامک عدم صدور قبض

قالب در `Aban360.Common/Literals/SmsTemplates.cs` با نام `NowGenerateBillFailed` ذخیره می‌شود:

```text
آبفا استان اصفهان
مشترک گرامی، درخواست صدور قبض برای شناسه قبض {0} انجام نشد.
علت: {1}
```

کنترلر شناسه قبض و متن عمومی دسته خطا را جایگزین می‌کند و پیامک را از طریق Hangfire و `ISmsOldHandler.SendNew` به شماره موبایل ورودی می‌فرستد. شماره موبایل باید ۱۱ رقم انگلیسی و با پیش‌شماره ۰۹ باشد. محدودیت روزانه نیز باعث ارسال پیامک عدم صدور می‌شود. علت دقیق در پیامک قرار نمی‌گیرد؛ متن و کد دقیق پاسخ API حفظ می‌شود.

متن‌های عمومی در همان فایل `SmsTemplates.cs` ذخیره شده‌اند:

| دسته | متن علت در پیامک |
| --- | --- |
| سقف روزانه | تعداد درخواست‌های مجاز روزانه تکمیل شده است. لطفاً روز بعد اقدام کنید. |
| اطلاعات اشتراک | صدور قبض برای این اشتراک امکان‌پذیر نیست. برای بررسی با امور مشترکین تماس بگیرید. |
| نیاز به بررسی کارکرد | کارکرد اعلام‌شده نیاز به بررسی دارد. لطفاً با امور مشترکین تماس بگیرید. |
| فاصله زمانی صدور | به دلیل صدور قبض اخیر، در حال حاضر امکان صدور قبض جدید وجود ندارد. |
| مشکل سامانه | درخواست شما در حال حاضر قابل انجام نیست. لطفاً در زمان دیگری اقدام کنید. |

برای تفکیک خطای احراز هویت از سایر خطاهای ۴۰۰ و صدور قبض اخیر از سایر خطاهای مصرف کم، دسته پیامک به‌صورت اطلاعات داخلی روی خروجی handler مشخص می‌شود. این اطلاعات وارد JSON پاسخ نمی‌شود. خطاهای پیش‌بینی‌نشده و اعتبارسنجی ورودی در دسته مشکل سامانه قرار می‌گیرند.

اگر قبض صادر شده باشد ولی مراحل بعدی مثل ارسال پیامک قبض خطا بدهد، پیامک عدم صدور ارسال نمی‌شود. خطای صف پیامک نیز پاسخ اصلی درخواست را تغییر نمی‌دهد و در گزارش خطای برنامه ثبت می‌شود.

پس از اجرای دستی اسکریپت، در محیط آزمایشی این موارد را نیز بررسی کنید:

1. برای یک موبایل، ده درخواست با شناسه‌های قبض متفاوت بفرستید؛ درخواست یازدهم باید کد ۱۰ بدهد.
2. برای یک شناسه قبض از چهار موبایل متفاوت درخواست بفرستید؛ درخواست چهارم باید کد ۱۱ بدهد.
3. برای یک شناسه قبض تازه، چهار درخواست هم‌زمان از موبایل‌های متفاوت بفرستید؛ تنها سه درخواست باید از کنترل سقف عبور کنند.
4. تمام درخواست‌ها، از جمله درخواست ردشده، باید سطر مستقل داشته باشند.
5. سطرهای روز قبل نباید در سقف امروز شمارش شوند.

قبض‌ها و موبایل‌های آزمایشی را طوری انتخاب کنید که محدودیت آزمون قبلی روی آزمون بعدی اثر نگذارد. عبور از کنترل سقف به معنی عبور از سایر قواعد صدور قبض نیست.
