# ثبت درخواست مشترک با تأیید پیامکی

## نصب دستی در Atlas

فایل `sql/001_SubscriberRequests_Atlas.sql` را روی سرور مقصد و با دیتابیس جاری **Atlas** اجرا کنید. اسکریپت بدون migration است، پایگاه داده نمی‌سازد، اطلاعات قبلی را حذف نمی‌کند و اجرای مجدد آن تعریف‌های نسخه ۱ موجود را بازنویسی نمی‌کند.

چهار جدول در schema به نام `SubscriberRequest` ساخته می‌شوند:

| جدول | کاربرد |
|---|---|
| `Definition` | کد enum، نسخه، عنوان، نام رشته‌ای Handler و قالب JSON اطلاعات |
| `Draft` | اطلاعات موقت، مالک درخواست، شماره مقصد، شناسه قبض، کد رهگیری و تصویر ثابت تعریف هنگام ثبت |
| `Challenge` | سابقه ارسال‌ها، هش کد، زمان انقضا و مصرف کد |
| `Submission` | درخواست نهایی ثبت‌شده برای رسیدگی توسط Handler پیش‌فرض |

این جدول‌ها به migration runner و EF Context اضافه نشده‌اند. حساب اتصال برنامه به مجوز خواندن جدول تعریف، خواندن و نوشتن سه جدول دیگر و گرفتن application lock در Atlas نیاز دارد.

## تنظیمات

در تنظیمات محیط اجرا مقدارهای زیر را قرار دهید. کلید واقعی را در کد یا مخزن ذخیره نکنید:

```json
{
  "ConnectionStrings": {
    "SubscriberRequestsConnection": "<connection string to the Atlas server>"
  },
  "SubscriberRequests": {
    "OtpHashKey": "<random secret containing at least 32 bytes>",
    "OtpLifetimeSeconds": 120,
    "MaxFailedAttempts": 5,
    "ResendCooldownSeconds": 30,
    "MaxSendsPer15Minutes": 5
  }
}
```

اگر `SubscriberRequestsConnection` تعریف نشود، سرور و اطلاعات ورود از `DefaultConnection` گرفته می‌شود؛ نام دیتابیس اتصال این قابلیت در هر دو حالت **Atlas** است. سرویس‌های موجود کاربر و استعلام اشتراک همچنان از اتصال‌های فعلی خود استفاده می‌کنند. تنظیمات `SmsOptions` موجود پروژه نیز باید آماده باشند.

کلید OTP باید بین تمام نمونه‌های API مشترک و در طول عمر کدها ثابت باشد. عمر کد از ۱ تا ۱۲۰ ثانیه قابل تنظیم است. تمام زمان‌ها UTC هستند. کد شش‌رقمی است و مقدار خام آن در جدول‌ها ذخیره نمی‌شود.

## API مشترک

تمام مسیرها از احراز هویت فعلی `BaseController` استفاده می‌کنند. شناسه مالک از توکن گرفته می‌شود و از بدنه درخواست پذیرفته نمی‌شود.

| متد | مسیر | کاربرد |
|---|---|---|
| GET | `/v1/subscriber-requests/definitions` | آخرین نسخه فعال تعریف‌ها و قالب اطلاعات |
| POST | `/v1/subscriber-requests` | اعتبارسنجی، ثبت موقت و ارسال کد |
| POST | `/v1/subscriber-requests/{id}/confirm` | تأیید و اجرای Handler |
| POST | `/v1/subscriber-requests/{id}/resend-code` | ارسال کد جدید |
| GET | `/v1/subscriber-requests/{id}` | وضعیت و نتیجه متعلق به همان مالک |

نمونه ثبت درخواست تغییر شماره:

```json
{
  "requestCode": 10031452100,
  "billId": "10018315",
  "payload": {
    "newMobile": "09123456789"
  }
}
```

نمونه بدنه تأیید:

```json
{ "code": "123456" }
```

شماره مقصد OTP از اطلاعات فعلی اشتراک خوانده می‌شود. پیاده‌سازی فعلی فقط زمانی اجازه ثبت می‌دهد که شماره همراه حساب واردشده با شماره اشتراک مطابقت داشته باشد. `payload.newMobile` مقصد OTP را تغییر نمی‌دهد. این کد اجازه ثبت درخواست تغییر شماره را تأیید می‌کند؛ احراز دسترسی به شماره جدید، در صورت نیاز کسب‌وکار، باید مرحله مستقل داشته باشد.

این نسخه برای اشتراک‌های دارای شناسه قبض است. «انشعاب جدید آب بدون اشتراک قبلی» در فهرست لینک ارائه‌شده وجود نداشت و در این مجموعه اضافه نشده است. پذیرش آن به سیاست شناسایی متقاضی مستقل و قرارداد ورودی جدا نیاز دارد.

## قالب و خطاها

`PayloadSchema` قالب اعتبارسنجی است، نه نمونه داده. اعتبارسنج فعلی زیرمجموعه صریح زیر از قواعد JSON Schema را اجرا می‌کند:

- نوع‌های `object`، `array`، `string`، `integer`، `number`، `boolean` و `null`؛ نوع در هر گره الزامی است.
- `properties`، `required` و `additionalProperties: false`؛ تمام objectها باید `properties` و ممنوعیت فیلد اضافه داشته باشند.
- `items`، `minItems` و `maxItems` برای آرایه‌ها.
- `minLength`، `maxLength` و `pattern` برای رشته‌ها؛ طول بر اساس Unicode code point محاسبه می‌شود.
- `minimum`، `maximum` و `enum` برای مقادیر ساده.
- `title` و `description` برای توضیح.

این اعتبارسنج پیاده‌سازی کامل استاندارد JSON Schema نیست؛ قواعد پشتیبانی‌نشده مانند `$ref`، `oneOf`، `format` و `if/then` خطای تنظیم قالب ایجاد می‌کنند و نادیده گرفته نمی‌شوند. قواعد وابسته به چند فیلد، استعلام‌ها، مجوزها و الزامات تخصصی در Handler کنترل می‌شوند. برای نمونه، در ادغام انشعاب، اجباری‌بودن `targetBillId` برای عملیات `merge` باید در Handler تخصصی بررسی شود.

نام فیلدها حساس به بزرگی و کوچکی حروف است. فیلد اضافه، تکراری، اجباری غایب، نوع نادرست یا مقدار خارج از قواعد با `SubscriberRequestPayloadException` رد می‌شود. این خطا از `BaseException` ارث می‌برد و خطاگیر فعلی API آن را با وضعیت ۴۰۰ برمی‌گرداند. اعتبارسنجی پیش از ذخیره و ارسال SMS انجام می‌شود و پیش از اجرای Handler نیز با قالب ذخیره‌شده تکرار می‌شود.

## Handler و تبدیل DTO

نام Handler در `Definition.HandlerName` ذخیره می‌شود. برنامه فقط نام‌های ثبت‌شده در مجموعه `ISubscriberRequestHandler` را می‌پذیرد؛ نام کلاس، assembly، متد یا پارامتر به کمک Reflection از دیتابیس اجرا نمی‌شود.

تمام تعریف‌های اولیه به `RegisterSubscriberRequestHandler` وصل هستند. این Handler درخواست را در `Submission` ثبت می‌کند و کد رهگیری می‌دهد. پایان پردازش در این API به معنی ثبت نهایی درخواست برای رسیدگی است؛ نتیجه عملیاتی خدمات مانند تغییر شماره، صدور قبض یا تعویض کنتور را اجرا نمی‌کند.

برای هر خدمت می‌توان Handler اختصاصی نوشت، آن را با `AddScoped<ISubscriberRequestHandler, YourHandler>()` ثبت کرد و نام آن را در نسخه جدید تعریف گذاشت. برای ورودی DTO از `TypedSubscriberRequestHandler<TPayload>` ارث ببرید؛ این پایه JSON ذخیره‌شده را با نام‌گذاری camelCase به DTO تبدیل می‌کند و فیلد ناشناخته و خطای تبدیل را رد می‌کند. نام پارامتر ورودی لازم نیست در دیتابیس ذخیره شود.

نوشتن نهایی و تغییر وضعیت باید در همان `ISubscriberRequestTransaction` انجام شوند. برای عملیات خارج از این تراکنش، مانند سرویس خارجی یا دیتابیس مستقل، Handler باید الگوی outbox یا idempotency بر اساس `request.Id` داشته باشد؛ قفل این ماژول به‌تنهایی برای تضمین یک‌بار اجراشدن اثر خارجی کافی نیست.

## نسخه‌بندی و تکرار عملیات

برای تغییر قالب یا Handler یک رکورد با همان `RequestCode` و نسخه بالاتر اضافه کنید. درخواست‌های جدید از آخرین نسخه استفاده می‌کنند؛ درخواست‌های قبلی قالب، داده و نام Handler زمان ثبت را نگه می‌دارند. Handlerهای نسخه‌های قبلی باید تا پایان آن درخواست‌ها در برنامه باقی بمانند. غیرفعال‌کردن آخرین نسخه، ثبت جدید آن خدمت را متوقف می‌کند.

ارسال مجدد فقط آخرین کد را فعال نگه می‌دارد و تعداد تلاش‌های ناموفق درخواست را صفر نمی‌کند. بعد از پنج تلاش اشتباه، درخواست قفل می‌شود. سقف ارسال در پنجره ۱۵ دقیقه‌ای برای مالک یا شماره مقصد اعمال می‌شود و ارسال ناموفق هم در این سقف حساب می‌شود.

در خطای سرویس پیامک، درخواست موقت و تلاش ارسال ذخیره می‌شوند؛ پیام خطا شناسه درخواست را برای ارسال مجدد اعلام می‌کند. تا ارسال موفق، کد قابل استفاده نیست.

بعد از تأیید صحیح، مصرف کد و وضعیت `Confirmed` ابتدا ثبت می‌شوند. سپس Handler در تراکنش جداگانه اجرا می‌شود. اگر Handler خطا بدهد، تأیید معتبر باقی می‌ماند و مالک می‌تواند همان مسیر `confirm` را برای تلاش مجدد فراخوانی کند؛ دریافت مجدد OTP لازم نیست. درخواست موفق نتیجه ذخیره‌شده را برمی‌گرداند و دوباره اجرا نمی‌شود. نوشتن‌های Handler در تراکنش ناموفق بازگردانده می‌شوند.

## منبع فهرست و وضعیت قالب‌ها

عنوان و کد ۲۸ خدمت از [فهرست خدمات CRM](https://crm.abfaesfahan.ir/10018315/direct) در تاریخ ۲۰۲۶/۱۱/۰۳ خوانده شد. لینک‌های قبض و سوابق که درخواست ثبت نمی‌کنند، وارد enum نشده‌اند. کدها از محدوده `int` بزرگ‌ترند؛ enum از `long` و ستون SQL از `bigint` استفاده می‌کند. `TrackingCode` در جدول درخواست، شناسه رهگیری مستقل از نوع خدمت است.

قالب‌های SQL، قرارداد اولیه این API هستند و استخراج قطعی همه فیلدهای سایت نیستند. فرم تغییر شماره قابل مشاهده بود؛ ورود به مرحله بعد فرم تغییر تعداد واحد در سایت با خطای داخلی روبه‌رو شد. قواعد و فیلدهای هر خدمت باید پیش از استفاده عملیاتی با نیاز کسب‌وکار تطبیق داده شوند.

## بررسی

آزمایش‌های مستقل از SQL Server و SMS واقعی:

```powershell
dotnet run --project tests/Aban360.SubscriberRequests.SmokeTests -- D:\Projects\Aban360
```

آزمایش‌ها شامل تطابق enum با ۲۸ تعریف SQL، اعتبارسنجی قالب و داده، انقضای دقیق ۱۲۰ ثانیه، مالکیت، قفل تلاش‌ها، ارسال مجدد، خطای پیامک، بازیابی خطای Handler و تأییدهای هم‌زمان هستند. برای آزمون هم‌زمانی از مخزن حافظه‌ای تراکنشی استفاده می‌شود؛ قفل‌ها، محدودیت‌ها و اسکریپت واقعی SQL باید بعد از نصب روی محیط آزمایشی Atlas بررسی شوند. اسکریپت در این کار روی دیتابیس واقعی اجرا نشده است.
