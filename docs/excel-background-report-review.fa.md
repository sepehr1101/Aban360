# بررسی ساخت اکسل در پس‌زمینه و اعلان SignalR

تاریخ: 2026-11-06

## مسیر فعلی

1. کنترلر `IReportGenerator.FireAndInform` را با ورودی، delegate متد handler، مشخصات کاربر، عنوان گزارش و شناسه اتصال فراخوانی می‌کند.
2. قرارداد handler از روی متد واقعی delegate و امضای ورودی/خروجی انتخاب می‌شود. قرارداد نامرتبط یا مبهم، قبل از ثبت درخواست رد می‌شود.
3. نوع ورودی، نوع سربرگ و ردیف، قرارداد handler و snapshot ورودی در `ReportPool.ServerReports` ثبت می‌شود.
4. کار از طریق `IBackgroundJobClient` در Hangfire صف می‌شود؛ اجرای آن به بازماندن درخواست HTTP یا اتصال SignalR وابسته نیست.
5. worker رکورد ذخیره‌شده را می‌خواند، نوع‌ها و امضای متد را بررسی و handler را از DI دریافت می‌کند.
6. ورودی با همان serializer مورد استفاده در ثبت، بازیابی و متد دقیق handler اجرا می‌شود.
7. فایل اکسل ساخته می‌شود؛ سپس ثبت تکمیل گزارش و مسیر فایل در دیتابیس انتظار داده می‌شود.
8. بعد از ذخیره موفق، `ReportCompletionNotifier` رویداد `InformReportCompletion` را برای شناسه مالک گزارش ارسال می‌کند.

ساختار رویداد تغییر نکرده است: `reportId`، `reportTitle` و `message`. مقصد، تمام اتصال‌های جاری مالک گزارش در محدوده پردازش/backplane تنظیم‌شده است؛ شناسه اتصال قدیمی، مقصد اعلان را تعیین نمی‌کند.

## نقص‌های اصلاح‌شده

| نقص | اصلاح |
| --- | --- |
| انتخاب اولین interface از کلاس handler | انتخاب قرارداد بر اساس متد واقعی delegate، نام متد و امضای ورودی/خروجی؛ در ابهام، خطای روشن پیش از ثبت درخواست. |
| ابهام در handler دارای overload | انتخاب متد با نام، نوع ورودی، پارامتر CancellationToken و نوع خروجی دقیق. |
| ثبت JSON با Newtonsoft و خواندن با System.Text.Json | هر دو طرف از Newtonsoft استفاده می‌کنند؛ نام‌گذاری سفارشی فیلدها حفظ می‌شود. |
| پیمایش تمام نوع‌های تمام اسمبلی‌ها برای بازیابی metadata | جست‌وجوی نام نوع ذخیره‌شده در اسمبلی‌های بارگذاری‌شده، همراه با بررسی نبود نوع و امضای نامعتبر. |
| موفق تلقی‌شدن خروجی null یا متد نامعتبر | job خطا می‌دهد، خطا در رکورد گزارش ثبت می‌شود و اعلان موفقیت ارسال نمی‌شود. |
| وابستگی تست و صف‌گذاری به `BackgroundJob.Enqueue` استاتیک | استفاده از `IBackgroundJobClient` و قرارداد `IReportGenerator` برای ایجاد job. |
| باقی‌ماندن درخواست مبهم در صورت خطای enqueue یا تولید | زمان خطا در ستون موجود `ErrorDateTime` ثبت می‌شود؛ خطای اصلی برای مسیر Hangfire/caller حفظ می‌شود. |
| تکرار ساخت گزارش تکمیل‌شده هنگام اجرای دوباره job | اگر مسیر ثبت‌شده هنوز به فایل موجود اشاره کند، همان فایل حفظ می‌شود و فقط اعلان می‌تواند دوباره ارسال شود. |
| نام فایل یکسان برای گزارش‌های هم‌نام در یک ثانیه | نام امن با پسوند GUID مستقل؛ گزارش‌ها فایل یکدیگر را بازنویسی نمی‌کنند. |
| نبود پوشه خروجی | پوشه هنگام ساخت مسیر فایل ایجاد می‌شود. |
| صفحه خالی اضافی برای تعداد ردیف مضرب اندازه صفحه | تعداد sheetهای داده دقیق محاسبه می‌شود. |
| شمارش و پیمایش چندباره enumerable ورودی | داده یک‌بار به snapshot قابل شمارش تبدیل می‌شود. |
| آزاد نشدن اتصال‌های دیتابیس ثبت درخواست و خواندن رکورد | اتصال‌ها با `await using` آزاد می‌شوند. |

مسیر ثبت تکمیل گزارش از بازبینی قبلی در تمام لایه‌ها `Task` است. ارسال اعلان بعد از `await` ذخیره نتیجه قرار دارد. خطای انتقال SignalR در notifier ثبت می‌شود و باعث ناموفق‌شدن گزارش تکمیل‌شده یا اجرای دوباره تولید آن نمی‌شود.

## وضعیت خطا و تلاش مجدد

برای ثبت خطا، ستون تازه‌ای لازم نیست. عملیات `Fail` فقط روی گزارش دارای `CompletionDateTime IS NULL`، زمان خطا را ثبت می‌کند؛ نتیجه‌ای که قبلاً کامل شده به‌اشتباه ناموفق نمی‌شود. تلاش موفق بعدی، زمان خطای قبلی را از طریق مسیر موجود ثبت تکمیل پاک می‌کند.

`ErrorDateTime` به معنی ثبت یک خطا در پردازش است؛ ممکن است Hangfire هنوز برای همان job تلاش مجدد انجام دهد. خطای ثبت خودِ وضعیت شکست، خطای اصلی پردازش را نمی‌پوشاند.

jobهایی که قبل از اصلاح، قرارداد اشتباه handler را ذخیره کرده‌اند ممکن است همچنان به خطا برسند؛ اطلاعات کافی برای حدس‌زدن قطعی قرارداد درست در آن رکوردها وجود ندارد. برای این موارد، گزارش از نسخه اصلاح‌شده دوباره درخواست شود.

## بررسی انجام‌شده

آزمون `tests/Aban360.ReportGeneration.SmokeTests` با handler و داده آزمایشی، فایل XLSX واقعی می‌سازد و فایل را به‌صورت ZIP/XML باز می‌کند. دیتابیس، صف Hangfire و انتقال SignalR در این آزمون شبیه‌سازی شده‌اند؛ هیچ اعلان واقعی به کاربر ارسال نمی‌شود.

نتیجه: هر ۱۹ بررسی مسیر اکسل موفق بود. همچنین مجموعه ۲۸ بررسی SignalR پس از این تغییرات دوباره ساخته و اجرا شد و همگی موفق بودند. بررسی‌های اکسل شامل:

- انتخاب interface درست کنار interface نامرتبط و متدهای overloadشده.
- حفظ ورودی JSON دارای `JsonProperty` و snapshot ورودی قبل از تغییر آن در caller.
- ادامه job پس از لغو درخواست HTTP.
- نرسیدن اعلان هنگام معطل‌بودن ذخیره نتیجه.
- ساخت فایل واقعی، تعداد صحیح sheetها و حذف ستون‌های مستثناشده.
- ارسال اعلان برای همان مالک و شناسه گزارش پس از ذخیره موفق.
- استفاده مجدد از فایل در اجرای دوباره job.
- متد جایگزین `HandleSummary`.
- نبود اعلان موفقیت در خطای handler، خروجی null، نوع یا متد نامعتبر و خطای ذخیره.
- حفظ فایل تکمیل‌شده هنگام خطای انتقال SignalR.
- ثبت شکست هنگام خطای enqueue.
- ساخت هم‌زمان دو گزارش هم‌نام در دو فایل مستقل.

در بازبینی سازگاری بعدی، مجموعه اکسل به ۲۶ بررسی گسترش یافت: دانلود با کنترلر موجود، Range و content type، اجرای مستقیم، گزارش خالی، هویت job قبلی و سازگاری metadata تعداد ۲۶۱ متد واقعی نیز تأیید شدند. هر ۱۳ مجموعه smoke پروژه موفق شدند. جزئیات و حدود اجرا در `docs/compatibility-regression-check.fa.md` ثبت شده است.

```powershell
dotnet run --project tests/Aban360.ReportGeneration.SmokeTests/Aban360.ReportGeneration.SmokeTests.csproj
dotnet run --project tests/Aban360.OnlineUsers.SmokeTests/Aban360.OnlineUsers.SmokeTests.csproj
```

## موارد لازم در محیط اجرا

- این اصلاح اکسل به تغییر schema جدیدی نیاز ندارد. اسکریپت حضور SignalR که قبلاً تحویل شده، همچنان پیش‌نیاز تغییرات کاربران آنلاین است.
- worker Hangfire باید فعال باشد و حساب اجرای برنامه دسترسی نوشتن به پوشه خروجی داشته باشد.
- ارسال SignalR رسید تحویل کلاینت نیست و پیام برای کاربر قطع‌شده ذخیره یا بازپخش نمی‌شود. فرانت همچنان باید پس از reconnect وضعیت گزارش‌ها را از API بازیابی کند.
- اعلان ممکن است در اجرای دوباره job، با همان `reportId` تکرار شود؛ فرانت با همان شناسه، وضعیت را به‌روزرسانی و اعلان تکراری را کنترل کند.
- ثبت درخواست و ثبت job در Hangfire هنوز دو عملیات جدا هستند. توقف ناگهانی پردازش دقیقاً میان این دو مرحله، با `catch` قابل مدیریت نیست. برای تضمین ثبت اتمیک در برابر این سناریو، الگوی outbox یا سازوکار بازیابی درخواست‌های بدون job لازم است؛ در این تغییر اضافه نشده است.
- کنترل استفاده مجدد از فایل، قفل توزیع‌شده برای اجرای هم‌زمان همان job نیست. پس از خطاهای خاص worker، تضمین exactly-once برای اجرای handler وجود ندارد؛ handler گزارش باید خواندنی و بدون اثر جانبی باشد.
- اتصال به SQL Server اصلی، اجرای worker واقعی Hangfire و دریافت WebSocket در مرورگر واقعی در این آزمون انجام نشده‌اند. پیش از انتشار، یک گزارش واقعی از فرانت درخواست و دسترسی دانلود آن پس از دریافت اعلان بررسی شود.
