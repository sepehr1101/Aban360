# اجرای تست‌ها

از ریشهٔ مخزن، همهٔ تست‌ها با این فرمان اجرا می‌شوند:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test.ps1
```

PowerShell 7 نیز پشتیبانی می‌شود؛ می‌توان به‌جای `powershell` از `pwsh` استفاده کرد. اسکریپت مستقل از پوشهٔ جاری، اجرای تست‌ها را از ریشهٔ مخزن انجام می‌دهد. SDK و runtime نسخهٔ .NET 8 و دسترسی به بسته‌های NuGet لازم است. نسخهٔ SDK نصب‌شده می‌تواند جدیدتر باشد، اما runtime هدف همچنان .NET 8 است.

## چه چیزهایی اجرا می‌شوند؟

- پروژه‌های `*.SmokeTests.csproj` زیر `tests` با `dotnet run`؛ این برنامه‌ها با خطای بررسی، کد خروج ناموفق می‌دهند.
- پروژه‌های تست در پوشه‌های پروژهٔ ریشه و زیر `tests`، با `dotnet test`؛ تشخیص براساس `IsTestProject` یا وابستگی `Microsoft.NET.Test.Sdk` است.
- فایل‌های `tests/*.Tests.ps1` در یک فرایند PowerShell مستقل.

کشف پروژه‌ها وابسته به عضویت در solution نیست. افزودن تست به همین ساختار، نیازی به افزودن نام آن به فهرست دستی ندارد. فایل‌ها و پوشه‌های تولیدشدهٔ `bin/obj` وارد فهرست تست نمی‌شوند.

شکست یک مجموعه مانع اجرای مجموعه‌های بعدی نمی‌شود. در پایان، جدول نتیجه و مسیر لاگ هر مجموعه در `artifacts/test-results/<run-id>/summary.json` ثبت می‌شود. برای پروژه‌های تست استاندارد، فایل TRX نیز ذخیره می‌شود. خروجی کلی فقط زمانی صفر است که تمام مجموعه‌های انتخاب‌شده موفق باشند. پروژهٔ بدون تست اجراشده، `Empty` یا در نبود TRX قابل بررسی، `Failed` است و موفق محسوب نمی‌شود.

## گزینه‌ها

```powershell
# فقط نمایش مجموعه‌ها؛ بدون build، restore و اجرا
.\scripts\test.ps1 -List

# اجرای یک مجموعه یا چند مجموعه با wildcard
.\scripts\test.ps1 -Suite 'Aban360.BankReceipt.SmokeTests','Aban360.Http*.SmokeTests'

# استفاده از بسته‌های قبلاً restore‌شده
.\scripts\test.ps1 -NoRestore

# پیکربندی Release
.\scripts\test.ps1 -Configuration Release
```

فیلتر بدون تطبیق خطاست تا غلط املایی باعث اجرای موفقِ بدون تست نشود. `-NoRestore` مرحلهٔ build را حذف نمی‌کند. لاگ‌ها و نتایج زیر `artifacts` هستند و وارد Git نمی‌شوند.

## حدود بررسی

تست‌های فعلی smoke عمدتاً از سرویس‌های بدل، حافظه و HTTP آزمایشی استفاده می‌کنند. runner خود API، migration یا job عملیاتی را راه‌اندازی نمی‌کند. تست تازه باید وابستگی محیطی و اثر جانبی خود را مستند کند.

چند smoke test فایل‌های منتخب تولید را مجدداً کامپایل می‌کنند؛ این‌ها برای رفتار همان بخش مفیدند، ولی جای build پروژهٔ واقعی و تست اتصال اجزا را نمی‌گیرند. AutoReading و OpenKm به پروژه‌های واقعی ارجاع دارند و تست‌هایی از ثبت وابستگی/رفتار اجزا دارند. آزمون یکپارچهٔ تراکنش روی SQL Server آزمایشی و نمونه‌های تأییدشدهٔ تعرفه همچنان باید همراه اصلاح همان مسیرها افزوده شوند.

پروژه‌های `Aban360.CalculationPoolTest.Api` و `Aban360.CalculationPoolTest.Application` فعلاً فایل تست ندارند. runner آن‌ها را مخفی یا موفق اعلام نمی‌کند. رفع این کمبود مستلزم افزودن تست معنادار برای رفتار مصوب همان بخش است.

## نتیجهٔ بررسی ۲۰۲۶/۱۱/۰۵

کشف و اجرای هر ۱۴ مجموعه بررسی شد. تست‌های خود runner با ۱۳ بررسی رفتاری روی Windows PowerShell و PowerShell 7 موفق بودند. هر ۱۲ مجموعهٔ دارای بررسی، با احتساب اجرای مجدد AutoReading پس از اصلاح fixture اطلاعات مشترک، موفق شدند؛ ارزیابی فرمول ۵۲ تست و AutoReading تعداد ۳۹ بررسی داشت. دو پروژهٔ خالی بالا همچنان باعث خروج کلی ناموفق می‌شوند. خروج ناموفق را با حذف یا نادیده‌گرفتن آن پروژه‌ها پنهان نکرده‌ایم.

اجرای ثبت‌شده از بسته‌های موجود با `-NoRestore` استفاده کرد. [جزئیات baseline و اصلاحات](../docs/code-maintainability-review.fa.md) در بخش پیگیری M04 آمده است.
