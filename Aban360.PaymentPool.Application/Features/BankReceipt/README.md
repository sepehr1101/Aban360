# ورود فایل وصول بانکی

این جریان در PaymentPool پیاده شده است. ساختار مبنا صفحات ۱۴ تا ۱۶ سند پرداخت غیرحضوری بانک‌هاست، با اصلاح کاربر: تمام تاریخ‌ها هشت‌رقمی شمسی `yyyyMMdd` هستند. تغییر تاریخ داخل نام فایل نیز همین‌طور در نظر گرفته شده است.

## API

تمام مسیرها تحت `v1/bank-receipt` و با احراز هویت اجرا می‌شوند. هر فایل فقط برای کاربر بارگذار قابل دسترسی است.

| مرحله | درخواست | ورودی / خروجی |
|---|---|---|
| Upload | `POST /upload` | multipart شامل `file` و `bankId`؛ خروجی `Id` |
| Validate | `POST /{id}/validate` | بررسی ساختار، نام فایل، بانک، تاریخ، شناسه‌ها، کانال، تعداد، جمع و پرداخت تکراری |
| Display | `GET /{id}/display` | Header، آمار واقعی، نام بانک، وضعیت، خطاهای فایل و حداکثر ۱۰ سطر تصادفی بدون تکرار |
| Reconcile | `POST /{id}/reconcile` | تمام سطرها، شامل سطرهای خراب از نظر ساختار، به همراه خطاها و شماره خط؛ خطاهای ساختار فایل در Display موجودند |
| Confirm | `POST /{id}/confirm` | JSON مانند `{"version":3,"confirmed":true}`؛ خروجی `UploaderId` |

پس از Reconcile، Display را مجدداً دریافت کنید. مقدار `Version` آخرین خروجی باید در Confirm ارسال شود. هیچ پرداختی قبل از تأیید در Credit ثبت نمی‌شود؛ اطلاعات مراحل قبلی در جدول موقت فرایند ذخیره می‌شود. با تکرار Confirm بعد از ثبت موفق، همان UploaderId برمی‌گردد.

در صورت هر خطای فایل یا سطر، ثبت کل فایل متوقف می‌شود؛ حذف یا ثبت بخشی از سطرها در این نسخه تعریف نشده است. Validate مجدد نتایج مغایرت‌گیری قبلی را باطل می‌کند. محتوای فایل ثبت‌شده تغییرپذیر نیست.

## قالب

فایل متنی ANSI با ارقام لاتین، بدون BOM و حداکثر ۱۰ مگابایت. پسوند مطابق سند، کد سه‌رقمی شرکت تابعه است و الزام `.txt` وجود ندارد. نمونه نام: `TEJ14040101WA001.091`.

Header با طول ۳۲:
`UtilityCode(1) + SubUtilityCode(3) + BankCode(2) + SendDate(8) + TotalPrice(10) + RecordNO(8)`

Detail با طول ۴۸:
`BranchCode(6) + ChannelType(2) + PayDate(8) + BillID(13) + PaymentID(13) + RefCode(6)`

مبلغ Header در هزار ریال است و در خروجی به ریال تبدیل می‌شود. مبلغ هر پرداخت از قسمت مبلغ شناسه پرداخت، بدون پنج رقم پایانی، استخراج و در ۱۰۰۰ ضرب می‌شود. کنترل ارقام شناسه مطابق الگوریتم موجود TransactionIdGenerator انجام می‌شود. صفرهای پیشرو شناسه‌ها برای تطبیق حذف می‌شوند. تاریخ اصلی و کد پیگیری در داده موقت و InsertLogInfo حفظ می‌شوند.

## تکمیل قواعد کسب‌وکار

`IBankReceiptReconciliationService` عمداً پیاده‌سازی پیش‌فرض ندارد. لازم است پیاده‌سازی آن در DI با همین interface ثبت شود و برای هر LineNumber نتیجه مستقل بدهد. قرارداد آن باید موارد زیر را بررسی کند:

- شناسایی شناسه قبض و مشترک در منابع معتبر؛
- تعلق کد شهر شناسه قبض به شهرهای آبفا اصفهان؛
- تطبیق شناسه پرداخت و مبلغ با صورتحساب/قسط؛
- پرداخت‌های تکراری در منابع تاریخی خارج از Credit.

نام‌های پیشنهادی کد خطا: `UnknownBillId`، `OutsideIsfahan`، `InvoiceMismatch` و `HistoricalDuplicate`. برای سطر معتبر InvoiceId و InvoiceInstallmentId واقعی برگردانید. در صورت نبود سرویس یا نبود پاسخ یک سطر، وضعیت ReconciliationPending ایجاد می‌شود و ثبت نهایی مسدود است. تشخیص اولیه غیرآبفا از رقم نوع خدمت شناسه قبض، قبل از این سرویس انجام می‌شود.

## ذخیره‌سازی و راه‌اندازی

Dapper نسخه `2.1.66` مطابق سایر ماژول‌ها اضافه شده است. Migration شماره `14050802` دو جدول BankReceiptImport و BankReceiptPaymentKey را در schema موجود PaymentPool می‌سازد. از مسیر فعلی migrationهای پروژه اجرا می‌شود؛ اجرای migration روی دیتابیس واقعی جزو تست‌های این تغییر نبوده است.

BankReceiptImport اطلاعات موقت، فایل اصلی، نتایج و نسخه فرایند را در Payload نگه می‌دارد. فایل تکراری در میان فایل‌های حذف‌نشده با SHA-256 محتوای اصلی تشخیص داده می‌شود. کلید پرداخت از BillId و PaymentId نرمال‌شده ساخته می‌شود؛ پرداخت‌های قبلی Credit نیز جداگانه بررسی می‌شوند. قاعده یکتایی یک پرداخت براساس همین دو شناسه است؛ در صورت تفاوت قواعد کسب‌وکار، باید این سیاست اصلاح شود.

Confirm با تراکنش Serializable، بررسی نسخه و محدودیت یکتایی، رکورد Uploader و تمام Creditها را اتمیک ثبت می‌کند. هم‌زمان کلیدهای پرداخت ثبت و فرایند نهایی می‌شود. شکست هر سطر تمام عملیات ثبت را برمی‌گرداند. پاکسازی یا انقضای فایل‌های موقت در این تغییر تعریف نشده است.

## بررسی

`dotnet run --project tests/Aban360.BankReceipt.SmokeTests`

تست مستقل بدون اتصال به دیتابیس است و کد واقعی parser و handler را اجرا می‌کند. برای کنترل تراکنش‌ها و migration، تست یکپارچه با SQL Server لازم است.

نتیجه بررسی این تغییر: ساخت کامل Aban360.Api با وابستگی‌ها موفق بود و ۷۰ بررسی smoke با موفقیت گذشت. هشدارهای موجود پروژه باقی هستند؛ تست SQL Server و اجرای migration انجام نشده است.

## گزارش مغایرت و شرح غیرقابل ویرایش

`POST v1/bank-receipt/discrepancy/report`

ورودی نمونه:
```json
{"fromDate":"1404/01/01","toDate":"1404/01/31","pageNumber":1,"pageSize":50,"hasDescription":null,"isActive":null}
```

تاریخ‌ها شمسی هستند و قالب `yyyyMMdd` نیز پذیرفته می‌شود. مبنا تاریخ بارگذاری فایل است؛ ابتدا و انتهای بازه هر دو لحاظ می‌شوند. مرز روز بر مبنای منطقه زمانی `Asia/Dubai` به UTC تبدیل می‌شود. حداکثر اندازه صفحه ۲۰۰ است. گزارش فقط وصولی‌های متعلق به فایل‌های کاربر جاری را برمی‌گرداند. `HasDescription` برای فیلتر دارای شرح/بدون شرح و `IsActive` برای مغایرت‌های جاری/رفع‌شده است؛ مقدار null هر دو وضعیت را شامل می‌شود.

هر ردیف شامل ImportId، LineNumber، نام بانک و فایل، زمان بارگذاری، شناسه قبض و پرداخت، مبلغ، تاریخ پرداخت، متن اصلی سطر و `Reasons` است. هر علت دو فیلد `Code` و `Message` فارسی دارد. `IsExcluded` و `ExclusionReasons` نیز در خروجی سطرهای Validate، Display و Reconcile وجود دارند و `ExcludedRecordCount` تعداد موارد کنارگذاشته‌شده را نشان می‌دهد. خطاهای عمومی Header/فایل به علت‌های هر وصولی مربوط اضافه می‌شوند. سطر خراب دیگر از خروجی حذف نمی‌شود و متن اصلی آن در RawData برمی‌گردد.

کدهای `UnknownCityCode`، `SubUtilityCode`، `UnknownBillId`، `OutsideIsfahan`، `InvoiceMismatch` و `HistoricalDuplicate` پیام فارسی مشخص دارند. متن انگلیسی یا خالی از سرویس مغایرت‌گیری با پیام فارسی جایگزین می‌شود و کد علت حفظ می‌شود. تعیین معتبر بودن واقعی کد شهر و شرکت تابعه همچنان بر عهده پیاده‌سازی قواعد مربوط است؛ تطبیق کد تابعه نام فایل و Header در parser انجام می‌شود.

برای ثبت شرح یک وصولی:

`POST v1/bank-receipt/discrepancy/{importId}/{lineNumber}/description`
```json
{"description":"کد شهر این وصولی در اطلاعات مرجع شناسایی نشد."}
```

شرح الزامی، حداکثر ۲۰۰۰ کاراکتر و فقط برای مغایرت فعال قابل ثبت است. متن نهایی، شناسه ثبت‌کننده و زمان UTC ثبت نگهداری می‌شوند. شرط اتمیک `Description IS NULL` فقط یک ثبت را، حتی در درخواست‌های هم‌زمان، می‌پذیرد. هیچ مسیر ویرایش یا حذف شرح وجود ندارد و trigger دیتابیس تغییر/حذف شرح ثبت‌شده و اطلاعات ثبت آن را مسدود می‌کند. `CanDescribe` در گزارش مشخص می‌کند ثبت شرح مجاز است یا خیر.

گزارش و شرح از Credit جدا هستند؛ ثبت شرح به‌معنای ثبت مالی وصولی یا معتبر شدن آن نیست. Validate/Reconcile مجدد شرح را پاک نمی‌کنند. در صورت رفع مغایرت، سابقه با IsActive=false و همان شرح حفظ می‌شود.

Migration شماره `1405080201` جدول BankReceiptDiscrepancy، شاخص گزارش، محدودیت شرح و trigger عدم تغییر را اضافه می‌کند. سطرهای قابل تجزیه فایل‌های قبلی هم از اطلاعات ذخیره‌شده به گزارش منتقل می‌شوند. برای بازیابی سطرهایی که parser قدیمی به دلیل خرابی ساختار ذخیره نکرده بود، Validate/Reconcile را دوباره اجرا کنید. این migration روی دیتابیس واقعی اجرا نشده است.

## فهرست بانک‌ها و حذف فایل‌های یک بانک در یک روز

`GET v1/bank-receipt/banks`

خروجی هر بانک شامل `Id` (شناسه داخلی مورد استفاده در Upload و حذف)، `BankName`، `CentralBankCode` (کد بانک مرکزی، به صورت رشته برای حفظ صفر ابتدایی) و `Identifier` (مشخصه سه‌حرفی) است. داده‌ها از همان جدول بانک‌های PaymentPool خوانده می‌شوند و فهرست جداگانه‌ای نگهداری نمی‌شود.

`POST v1/bank-receipt/delete-by-bank-date`
```json
{"bankId":1,"uploadDate":"1404/01/01"}
```

قالب `14040101` نیز پذیرفته می‌شود. مبنا روز بارگذاری فایل با همان منطقه زمانی و قواعد گزارش مغایرت است؛ تاریخ Header یا تاریخ پرداخت معیار حذف نیست. API فقط فایل‌های کاربر جاری در بانک و روز تعیین‌شده را حذف منطقی می‌کند. شناسه بانک باید `Id` خروجی فهرست بانک‌ها باشد، نه کد بانک مرکزی.

خروجی شامل `DeletedFileCount` (تعداد فایل‌های حذف‌شده) و `CommittedFileCount` (تعداد فایل‌هایی از میان آن‌ها که قبلاً تأیید و ثبت نهایی شده بودند) است. روز بدون فایل و درخواست تکراری هر دو خروجی صفر دارند. این عملیات فقط حذف فایل از جریان است؛ Creditها و کلیدهای کنترل پرداخت تکراری حفظ می‌شوند و برگشت مالی انجام نمی‌شود.

فایل حذف‌شده در Validate، Display، Reconcile و Confirm در دسترس نیست. اجرای هم‌زمان حذف و ثبت/صحت‌سنجی با تراکنش و شرط IsDeleted کنترل می‌شود. مغایرت‌های فایل غیرفعال می‌شوند؛ شرح‌ها و اطلاعات ثبت آن‌ها حذف یا تغییر نمی‌کنند و همچنان در گزارش سوابق قابل مشاهده‌اند. شناسه و زمان UTC حذف در DeletedBy و DeletedAt ثبت می‌شوند.

پس از حذف، بارگذاری مجدد همان محتوا مجاز است. اگر پرداخت‌های فایل قبلاً ثبت شده باشند، کنترل تکراری بودن آن‌ها همچنان مانع ثبت مالی مجدد می‌شود.

Migration شماره `1405080202` ستون‌های BankId، UploadedAt و اطلاعات حذف را به جدول فرایند اضافه می‌کند؛ اطلاعات فایل‌های قبلی را پر می‌کند و شاخص انتخاب بانک/روز و یکتایی فایل‌های حذف‌نشده را می‌سازد. بازگشت migration در صورت وجود محتوای دوباره بارگذاری‌شده مسدود می‌شود تا سوابق به صورت خودکار حذف نشوند. Migration روی SQL Server واقعی اجرا نشده است.
